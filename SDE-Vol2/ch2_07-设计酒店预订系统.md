> **本章定位**:酒店预订是**"低 TPS 高并发尖峰 + 强一致 + 并发抢占"**的业务系统题——它是 Marriott/Booking/携程/美团的预订核心,也是**秒杀/抢购/库存类题的祖型**。它把 Vol.1 Ch1 的缓存/分片、ACID 事务、V2-Ch4 的幂等全用上。灵魂是五件事:**① 业务建模(订房型不订具体房 ⭐)② 并发双重预订怎么防(幂等 key + 悲观/乐观锁/CHECK 约束 ⭐⭐⭐)③ 房型库存表设计(一行一日期,room_type_inventory)④ 超售(10% overbooking)⑤ 微服务数据一致性(2PC vs Saga)**。它是国内大厂"秒杀/库存/订单"三件套的面试标准答案。

> **本章和原书的区别**:原书把**并发双重预订讲得极透彻**——幂等 key 防重复点击、悲观/乐观锁/CHECK 约束防竞争条件、room_type_inventory 表设计、超售实现都覆盖,是面试标准答案。但**没把这道题和"秒杀/抢购"挂钩**——而酒店+超售本质就是秒杀(高并发抢有限库存),这是国内大厂高频题的连接点;**锁只讲 DB 级(悲观/乐观/CHECK),没讲 Redis 级(Lua 原子预扣 + Redlock)**——2026 秒杀的实际做法是 Redis Lua 原子扣减库存,把并发挡在 DB 之外;**Saga 只提名字没讲透**——现代用 **Outbox 模式**可靠发事件;**微服务一致性 hybrid 方案很务实**但没讲清楚为什么;**定价只说"动态",没讲 ML 收益管理**(航空式按预测定价)+ **超售比例靠 ML 预测 no-show**。本章把这些补上。

**原书确定的需求**:

| 维度 | 确认值 |
|------|--------|
| 规模 | **5000 酒店,100 万房** |
| 付款 | 预订时**全款**付 |
| 渠道 | 官网 / App |
| 取消 | 支持 |
| **超售** ⭐ | **允许 10%**(预期有人取消) |
| 定价 | **动态**(每天不同,看满房率) |
| 聚焦 | 酒店页/房型详情页/预订/管理后台/超售(**搜索不在范围**) |

**非功能性**:**高并发**(旺季/大事件,热门房型被抢);**中等延迟**(几秒可接受)。

**估算**(背):

```
70%入住率, 平均住3天
日预订量 = (100万 × 0.7) / 3 ≈ 24万
预订 TPS = 24万 / 10^5 ≈ 3 TPS  ⚠️ 均值很低!

★ 漏斗(每步90%流失):
  详情页 300 QPS → 预订页 30 QPS → 下单 3 TPS
★ 但: 旺季/大事件 热门房型瞬时高并发(秒杀特征)
```

> 💡 **核心洞察**:**均值 TPS 只有 3,但旺季热门房型瞬时高并发**——这是"低均值 + 高尖峰"的秒杀特征。**架构要为尖峰设计**(锁/缓存扛并发),不能只看均值。

## 2. 业务建模:订房型不订具体房 ⭐⭐⭐⭐⭐(核心洞察)

> 📝 **关键业务洞察**:**酒店预订订的是"房型"(标准间/大床房/双床房),不是具体房间号**。房间号是 **check-in 时才分配**的。这和 Airbnb(订整个 listing,有具体 ID)根本不同。

```mermaid
flowchart LR
    BAD["❌ 朴素建模(Airbnb式)<br/>订 room_id(具体房)<br/>不适合酒店"]
    GOOD["✅ 正确建模<br/>订 room_type_id(房型)<br/>check-in才分具体房 ⭐"]

    style BAD fill:#FFEBEE,stroke:#C62828,color:#1f1f1f
    style GOOD fill:#E8F5E9,stroke:#388E3C,color:#1f1f1f
```

> 🪤 **追问陷阱(高频)**:"酒店预订和 Airbnb 预订的数据模型区别?" → "**Airbnb 订具体 listing(有 listing_id);酒店订房型(room_type),具体房间号 check-in 才分配**。所以酒店的库存表是**按房型+日期**统计余量,不是按具体房间。这是本题最关键的业务洞察——**很多人一上来按 Airbnb 建模就错了**。"

## 4. 并发双重预订 ⭐⭐⭐⭐⭐(本章灵魂)

两个场景:**① 同一用户重复点击 ② 多用户同时抢同一房型**。

### 4.1 场景一:同一用户重复点击 → 幂等键

```mermaid
sequenceDiagram
    participant U as 用户
    participant API as Reservation API
    participant DB
    U->>API: 提交预订1(reservation_id=X)
    API->>DB: INSERT (PK=X)
    DB-->>API: 成功
    Note over U: 网络卡, 又点一次
    U->>API: 提交预订2(reservation_id=X)
    API->>DB: INSERT (PK=X)
    DB-->>API: ❌ 唯一约束冲突(主键重复)
    Note over API: 第二次被拒 → 防双订
```

**解法**:**reservation_id 作主键(PK)**,靠**唯一约束**——第二次插入主键冲突被拒。

```mermaid
flowchart LR
    Q["防重复点击"] --> C1["客户端: 灰掉按钮(不可靠)"]
    Q --> C2["API: 幂等键 reservation_id ⭐<br/>+ DB 主键唯一约束"]

    style Q fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style C1 fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style C2 fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
```

> 💡 **幂等键**接 Vol.1 Ch1 的幂等思想——**reservation_id 由全局唯一 ID 生成器产生**(接 Vol.1 Ch7),作为幂等键。客户端禁用按钮(灰掉)是辅助但不可靠(可禁 JS)。

### 4.2 场景二:多用户同时抢 → 竞争条件(race condition)⭐⭐⭐

```mermaid
sequenceDiagram
    participant T1 as 事务1(用户A)
    participant T2 as 事务2(用户B)
    participant DB
    Note over DB: 库存: total=100, reserved=99(剩1间)
    T1->>DB: SELECT(剩1, 校验99+1<=100 ✅)
    T2->>DB: SELECT(剩1, 校验99+1<=100 ✅)
    Note over T1,T2: 两事务都读到99, 都以为够
    T1->>DB: UPDATE reserved=100
    T2->>DB: UPDATE reserved=100
    Note over DB: 💀 超卖! 售出2间实际只1间
```

**根因**:**非串行化隔离级别**下,事务1的修改在提交前对事务2不可见(ACID 的 I),两事务都读到旧值 99,都通过校验,都更新 → 超卖。

> 🪤 **追问陷阱**:"为什么 ACID 的隔离性反而导致超卖?" → "隔离性(I)保证事务未提交的修改别人看不到。所以事务1改了 reserved=100 但没提交时,事务2 SELECT 仍读到旧的 99,通过校验后也改成 100 → 超卖。**隔离性是双刃剑:保证一致的同时制造了读旧值窗口**。解法是加锁或约束。"

### 4.3 三种解法(背熟对比)⭐⭐⭐

```mermaid
flowchart TD
    LOCK["解竞争条件"] --> P["① 悲观锁<br/>SELECT...FOR UPDATE"]
    LOCK --> O["② 乐观锁 ⭐<br/>version 字段"]
    LOCK --> C["③ DB CHECK 约束<br/>(total-reserved>=0)"]

    style LOCK fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style P fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style O fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style C fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
```

| 方案 | 机制 | 优 | 劣 | 适用 |
|------|------|----|----|------|
| **① 悲观锁** | `SELECT...FOR UPDATE` 锁行,他人等 | 简单,序列化更新 | **死锁**;长锁伤性能,不可扩展 | ❌ **不推荐**(预订) |
| **② 乐观锁 ⭐** | version 字段;更新时校验 version+1 | 不锁 DB,快 | **高并发下重试风暴**(只有一个成功) | ✅ **酒店(QPS低)** |
| **③ CHECK 约束** | `CHECK(total_inventory-total_reserved>=0)` | 易实现 | 高并发失败多;不跨库可移植 | ✅ **酒店(低争用)** |

#### 乐观锁详解(推荐)

```mermaid
sequenceDiagram
    participant A as 用户A
    participant B as 用户B
    participant DB
    A->>DB: 读 version=5
    B->>DB: 读 version=5
    A->>DB: UPDATE SET reserved+1, version=6 WHERE version=5
    DB-->>A: ✅ 成功(version变6)
    B->>DB: UPDATE SET reserved+1, version=6 WHERE version=5
    DB-->>B: ❌ 失败(version已是6≠5)→ 重试
```

**乐观锁**:加 `version` 列;读时记 version;更新时 `WHERE version=旧值`,version+1。**校验失败则重试**。

> 💡 **为什么推荐乐观锁给酒店?** 酒店预订 **QPS 低**(均值 3 TPS),**数据争用少**——乐观锁在低争用下几乎不重试,又不像悲观锁那样锁 DB。**高争用场景(秒杀)乐观锁会重试风暴**(只有一个成功,其余全失败重试),这时要换 Redis 预扣(见第 9 节)。

## 5. room_type_inventory 表设计 ⭐⭐⭐⭐⭐


**关键设计**:**一行一个日期**——这让日期范围内的查询和管理极简单。

| 方案 | 机制 | 优劣 |
|------|------|------|
| **2PC** | 跨节点原子提交(全成或全败) | 阻塞,单点故障卡死,**性能差** |
| **Saga ⭐** | 本地事务序列;每步发消息触发下一步;失败执行**补偿事务** | 最终一致,非阻塞;但要写补偿逻辑 |

### 8.2 Redis Lua 原子预扣(秒杀实际做法)⭐⭐⭐

原书锁都在 DB 级(悲观/乐观/CHECK)。但**秒杀的实际做法是把并发挡在 DB 之前——Redis Lua 原子扣减**。

```mermaid
flowchart LR
    REQ["下单请求<br/>(高并发)"] --> R["Redis Lua 原子操作<br/>检查+扣减在一个Lua脚本"]
    R -->|"库存够"| OK["预扣成功<br/>(DB异步落账)"]
    R -->|"库存不够"| FAIL["直接拒绝<br/>(DB完全不碰)"]
    NOTE["Lua脚本原子执行<br/>→ 无竞争条件<br/>→ DB只收到已预扣的请求"]

    style REQ fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style R fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style OK fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style FAIL fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style NOTE fill:#90CAF9,stroke:#1976D2,color:#1f1f1f
```

> 📝 **Redis Lua 预扣**:用 Lua 脚本在 Redis 里**原子地"检查库存 + 扣减"**(Lua 单线程执行,天然无竞争)。库存不够直接拒(不碰 DB)。预扣成功的请求再异步落 DB。**把高并发挡在 Redis,DB 只处理已预扣的**——这是秒杀扛 10 万 QPS 的核心。
>
> 🔄 **2026 现代版话术**(原书锁都在 DB):
> "原书的悲观/乐观/CHECK 锁都在 DB 级,酒店低 QPS 够用。但**真秒杀(10万+ QPS)DB 锁扛不住**。生产做法:**Redis Lua 原子预扣库存**——Lua 脚本单线程执行天然无竞争,检查+扣减原子完成,库存不够直接拒(不碰 DB),预扣成功再异步落 DB。**把并发挡在 Redis 之前**,DB 只收到已预扣的请求。**这是秒杀扛超并发的核心模式**。"

## 💻 代码示例

### 示例 1:乐观锁防并发(SQL)

```sql
-- 读时记 version
SELECT date, total_inventory, total_reserved, version
FROM room_type_inventory
WHERE room_type_id = ? AND hotel_id = ? AND date BETWEEN ? AND ?;

-- 应用校验每行: total_reserved + n <= 1.1 * total_inventory
-- 更新时带 version(乐观锁)
UPDATE room_type_inventory
SET total_reserved = total_reserved + ?,
    version = version + 1
WHERE room_type_id = ? AND hotel_id = ? AND date BETWEEN ? AND ?
  AND version = ?;   -- 乐观锁: version 必须匹配
-- 受影响行数 < 预期 → 并发冲突 → 重试
```

### 示例 2:CHECK 约束防超卖

```sql
ALTER TABLE room_type_inventory
ADD CONSTRAINT chk_room_count
CHECK (total_inventory - total_reserved >= 0);
-- 超卖时 reserved > inventory → 约束违反 → 自动回滚
```

### 示例 3:Redis Lua 原子预扣(秒杀核心)

```lua
-- KEYS[1] = 库存key  KEYS[2] = 已售key  ARGV[1] = 抢购数  ARGV[2] = 用户id(幂等)
local stock = tonumber(redis.call('GET', KEYS[1]))
local sold = tonumber(redis.call('SCARD', KEYS[2]))   -- 已售用户集合
local want = tonumber(ARGV[1])
local user = ARGV[2]

if redis.call('SISMEMBER', KEYS[2], user) == 1 then
    return -2   -- 已抢过(幂等防重)
end
if stock - sold < want then
    return -1   -- 库存不足(拒绝, 不碰DB)
end
redis.call('SADD', KEYS[2], user)   -- 标记已抢
return stock - sold - want          -- 返回剩余库存(预扣成功)
-- 整个脚本原子执行, 天然无竞争
```

## 🪤 追问陷阱(面试官最爱问,本章集)

1. **"酒店预订和 Airbnb 区别?"** → 酒店订**房型**(check-in 分房),Airbnb 订具体 listing。库存表按房型+日期,不是按房间。
2. **"为什么用关系库?"** → 读重写轻 + **ACID**(防超卖/双扣)+ 结构清晰。NoSQL 弱一致不适合预订。
3. **"怎么防同一用户重复下单?"** → **reservation_id 幂等键 + 主键唯一约束**。客户端灰按钮是辅助不可靠。
4. **"多用户同时抢最后一间怎么办?"** → 锁。悲观(`FOR UPDATE`)/乐观(version)/CHECK 约束三选一。
5. **"悲观锁为什么不适合预订?"** → 死锁 + 长锁伤性能 + 不可扩展。
6. **"乐观锁高并发会怎样?"** → **重试风暴**(只有一个成功,其余全失败重试)。酒店 QPS 低够用,秒杀不行。
7. **"乐观锁和 CHECK 约束区别?"** → 乐观锁靠应用 version 校验;CHECK 靠 DB 约束自动回滚。CHECK 更简单但不可移植。
8. **"ACID 隔离性为什么导致超卖?"** → 未提交修改别人看不到,两事务都读旧值通过校验。解法是锁/约束。
9. **"room_type_inventory 为什么一行一日期?"** → 日期范围查询/管理简单(`WHERE date BETWEEN`)。
10. **"超售怎么实现?"** → 校验放宽到 `reserved+n ≤ 110% × inventory`。
11. **"分片键选什么?"** → **hotel_id**(大部分查询先选酒店)。
12. **"缓存和 DB 库存不一致?"** → DB 先更新 + CDC 异步同步缓存;**DB 做最终校验就不影响正确性**(缓存多报被 DB 拒)。
13. **"微服务怎么保证跨服务一致?"** → 2PC(阻塞差)/ **Saga**(本地事务+补偿,最终一致)。原书选 hybrid 同库单事务(务实)。
14. **"Saga 中间态可见怎么办?"** → 业务展示"处理中"+ 状态机 + 幂等键(接 Vol.1 Ch1)。
15. **"这是秒杀吗?"** → **是!** 高并发抢有限库存。秒杀实际用 **Redis Lua 原子预扣**把并发挡在 DB 之前,不是 DB 锁。
16. **"预扣后用户不付怎么办?"** → 限时支付(15分钟)+ 超时自动还库存(防占着不放)。
17. **"微服务怎么可靠发事件?"** → **Outbox 模式**(业务+事件同事务写,CDC 读 outbox 发 Kafka,保证不丢)。

**核心 Takeaways**:

1. **核心业务洞察**:订**房型不订具体房**(check-in 才分房)——区别于 Airbnb。很多人这里就错了。
2. **关系库**:读重写轻 + **ACID**(防超卖/双扣)+ 结构清晰。预订默认关系库。
3. **防双重预订**:① 幂等键(reservation_id 主键)防重复点击;② 锁防并发竞争。
4. **三种锁**:悲观(`FOR UPDATE`,不推荐)/ **乐观(version,推荐低QPS)**/ CHECK 约束。酒店选乐观锁。
5. **room_type_inventory**:一行一日期,复合主键 (hotel_id, room_type_id, date),预生成 2 年;超售放宽到 110%。
6. **分片按 hotel_id**;Redis 缓存库存 + **DB 做终审**(缓存不一致不影响正确性)。
7. **微服务一致性**:2PC(差)/ **Saga**(补偿,最终一致);原书务实选 hybrid 同库单事务。
8. **架构师权衡**:微服务纯派每服务独立库很优雅,但 Saga 复杂度大——**本题不值,同库 ACID 务实**。
9. **本质 = 秒杀**(国内大厂高频题);真秒杀用 **Redis Lua 原子预扣**把并发挡在 DB 之前,DB 锁扛不住。
10. **预扣 + 限时支付 + 超时还库存**(电商标准模式);**Outbox 模式**可靠发事件;**ML 定价/超售预测**是收益管理。

> 🔗 **连接上下章**:**V2-Ch6 广告聚合**(流式大数据)是"写重无状态";**V2-Ch7 酒店预订**是"高并发强一致有状态"(锁/事务)——从流处理切回业务交易系统。**V2-Ch8 分布式邮件**继续业务系统,但换到"异步可靠投递"场景(SMTP/IMAP + 队列 + 送达率)。

**Day 0 选型理由(原书)**:数据有天然关系(property → rooms → bookings),需要 **ACID 保证预订只对可用房确认**(书页 871)。Aurora 单库 128 TB 存储绰绰有余(估算 730 GB/年),**垂直扩展 + 多 AZ 高可用就够**,不需要分库。

**关键:把 room_type_inventory 落到 Aurora PostgreSQL 事务**

本章 5 节的 room_type_inventory 表(一行一日期、复合主键 hotel_id+room_type_id+date)在 Aurora 上**一模一样能跑**——核心是把"校验 + 扣减"包进**单事务**:

```sql
-- BEGIN;
-- ① 乐观锁: 校验 version 并扣减(防并发抢占, 本章 4.3 节)
UPDATE room_type_inventory
SET total_reserved = total_reserved + :n,
    version = version + 1
WHERE hotel_id = :hid AND room_type_id = :rtid
  AND date BETWEEN :start AND :end
  AND version = :v                          -- 乐观锁: version 必须匹配
  AND total_reserved + :n <= 1.1 * total_inventory;  -- 超售校验 110%
-- 受影响行数 < 范围天数 → 并发冲突或超售 → ROLLBACK + 重试
-- ② INSERT reservation(idempotency_key, ...) -- 幂等键防重复点击
-- COMMIT;
```

**悲观锁变体**(单间高争用,如最后一间):

```sql
-- BEGIN;
-- SELECT ... FROM room_type_inventory
-- WHERE hotel_id=:hid AND room_type_id=:rtid AND date BETWEEN :start AND :end
-- FOR UPDATE;   -- 行锁, 他人等(本章 4.3 节悲观锁)
-- 校验 total_reserved+n <= 110%*total
-- UPDATE ... ; INSERT reservation ... ;
-- COMMIT;
```

> 🪤 **追问陷阱**:"Aurora 上用乐观锁还是悲观锁?" → **酒店预订 QPS 低(均值 3 TPS,本章 1 节),数据争用少,首选乐观锁**(version 列 + WHERE version=:v,失败重试)。悲观锁(`FOR UPDATE`)在死锁和高并发下伤性能,**只在"最后一间房"这种极端争用时临时用**。原书明确说 hotel booking 数据争用不严重,乐观锁够用(书页 882)。

**Lambda 处理器示例(预订 = 校验 + 扣减 + 落单,单事务)**:

```python
import boto3, json, os
pg = boto3.client('rds-data')  # Aurora Serverless v2 Data API
resource_arn = os.environ['AURORA_ARN']; secret_arn = os.environ['SECRET_ARN']

def reserve_handler(event, context):
    """API Gateway 触发: 幂等键在 header x-idempotency-key"""
    body = json.loads(event['body'])
    idem_key = event['headers']['x-idempotency-key']  # = 本章 reservation_id
    hid, rtid = body['hotelID'], body['roomTypeID']
    start, end, n = body['startDate'], body['endDate'], int(body['roomCount'])
    try:
        # 单事务: 校验+扣减库存 + 落订单(幂等键防双订)
        pg.execute_statement(
            resourceArn=resource_arn, secretArn=secret_arn,
            database='hotel',
            sql="""
            BEGIN;
            UPDATE room_type_inventory
              SET total_reserved = total_reserved + :n, version = version + 1
              WHERE hotel_id=:hid AND room_type_id=:rtid
                AND date BETWEEN :start AND :end
                AND total_reserved + :n <= 1.1 * total_inventory;
            INSERT INTO reservations(idempotency_key, hotel_id, room_type_id, start_date, end_date, rooms, status)
              VALUES (:idem, :hid, :rtid, :start, :end, :n, 'PENDING_PAYMENT')
              ON CONFLICT (idempotency_key) DO NOTHING;  -- 幂等防重
            COMMIT;""",
            parameters=[...])
        return {'statusCode': 200, 'body': json.dumps({'status':'reserved'})}
    except Exception as e:  # 超售 or 冲突
        return {'statusCode': 409, 'body': json.dumps({'error':'no_availability'})}
```

> 💡 **三件套逻辑**:① `UPDATE ... WHERE version + 超售校验` 防并发超卖(乐观锁,本章 4.3);② `ON CONFLICT DO NOTHING` 防重复点击(幂等键,本章 4.1);③ 全部包在单事务,要么全成要么全败(ACID,本章 2.1)。**Aurora 把这三个根本问题一次解决**。

**① Aurora 多 AZ + 跨 Region 读副本(DR)**:Aurora 写 6 副本跨 3 AZ,主挂秒级提升副本;**跨 Region 读副本**做灾难恢复(主 Region 整体挂时切到备 Region)。这是"容错 = 复制 + 检查点"(aws_01 第 2.7 节)在 AWS 上的标准落地。

**② Idempotency 全链路**:预订涉及钱,**必须保证客户只扣一次**。原书引用 Airbnb 的 Orpheus 幂等库(书页 886),AWS 上对应:① **API Gateway 透传客户端 idempotency-key**;② **DynamoDB 事务用 clientToken**(原书原话:"clientToken is valid for a 10-minute time window and ensures idempotent behavior",书页 886);③ **Aurora 用 `ON CONFLICT DO NOTHING` + 主键唯一**。**每个支付分 pre-RPC / RPC / post-RPC 三步**(原书图 18-9):pre-RPC 记 intent 到库,RPC 调外部网关,post-RPC 处理回调——**数据库调用和外部网络调用严格分开**,这是幂等设计的工程精髓。

**③ 峰值弹性(节假日)**:旅游旺季/大事件流量尖峰(本章 1 节"秒杀特征")。Aurora 应对:① **加读副本(最多 15 个)** 扛读流量;② **Aurora Serverless v2** 按 ACU 自动伸缩(峰值秒级扩容,低谷自动缩,适合不可预测流量);③ 写还是走单 writer 实例(可垂直升配)。

**④ 分布式 Saga**:复杂批量预订(旅行社一次订几十间、跨多酒店)用 **Step Functions Distributed Map**(2022+ 新特性)——一个 Map state 并行处理上千子任务,每个子任务是一个独立 Saga 子流程。**原书讲 Aurora Limitless 分布式事务用两阶段提交**(书页 896)——多 shard 事务的 ACID 由 transaction router 保证。

**⑤ 支付 webhook + SQS 解耦**:外部支付网关(PayPal/UPI)异步回调,直接打 SQS 而不是同步调预订服务——**削峰 + 解耦 + 重试 + DLQ**(aws_12 SQS 核心场景)。预订服务消费 SQS 更新预订状态,**乱序/重复事件由消费端处理**(原书书页 889:丢弃已到终态的中间事件、内置 inquiry 机制)。

**⑥ SNS + SES 多渠道通知**:预订状态变更(CONFIRMED/CANCELLED/REFUNDED)发 SNS 主题,fan-out 到 SES(邮件)、SMS、push、WhatsApp。原书 Day N 架构(图 18-17)明确把通知做成独立组件。

### 💰 成本与性能

| 选型权衡 | Day 0(省钱) | Day N(性能/规模) | 触发切换的信号 |
|---------|------------|----------------|--------------|
| **Aurora vs Aurora Serverless v2** | 流量稳定 → **按实例**(可预测便宜) | 流量尖峰大 → **Serverless v2**(ACU 弹性) | 旺季 QPS 波动 > 3× |
| **Aurora 副本数** | 1-2 读副本 | 读副本扩到 15 + 跨 Region DR | 读延迟 p99 > 100ms |
| **ElastiCache** | 单节点(读 QPS 低) | Cluster mode + 副本(读多 + 高可用) | 缓存命中率 < 90% |
| **DynamoDB 容量** | On-Demand(不可预测) | Provisioned + Auto Scaling(可预测省) | 流量稳定可预估 |
| **搜索** | DynamoDB GSI(简单筛选) | OpenSearch 集群(全文/模糊/地理) | 筛选维度 > 5 或要模糊 |
| **Step Functions** | Standard(长 Saga,可审计) | Express(高并发短流程,1/4 价) | 状态转换 > 4K/s |

> 💡 **Aurora 选型口诀**:**流量可预测且稳定 → 按实例**(预留,便宜);**流量尖峰大或不可预测(节假日)→ Serverless v2**(ACU 弹性,贵但省心)。**ElastiCache 是省钱大户**——把 90% 的可用性查询挡在 Aurora 之外,DB 压力骤降,可少开副本。**Step Functions 按状态转换次数计费**(Standard 每 1000 次转换约 $0.025),复杂 Saga 要算状态数——简单 2-3 步链式改用 Lambda + SQS 更便宜。

> 🪤 **成本陷阱**:**Step Functions Distributed Map 大批量并行会爆账单**——一次 Map 跑 1 万个子状态 = 1 万次转换计费。批量场景要么用 Express Workflow(便宜 1/4),要么改 SQS + Lambda fan-out。**跨 Region 读副本的数据传输费**也是隐藏成本(aws_01 八谬误之"传输免费")。
