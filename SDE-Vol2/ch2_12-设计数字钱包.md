# Volume 2 · Chapter 12: 设计数字钱包 (Design a Digital Wallet)

> **本章定位**:数字钱包是**"金融级强一致 + 复式记账 + 防双花 + 可重放审计"**的账户系统题——它是 PayPal / 支付宝余额 / 微信钱包 / M-Pesa 的设计骨架。它把 Vol.1 Ch1 的一致性/CAP、V2-Ch11 支付系统的事务/幂等全深化到**账户级**。灵魂是六件事:**① 钱包余额为什么必须强一致(钱不能凭空多/少)② 怎么防双花(double-spending,余额被并发扣超)③ 跨账户转账怎么做分布式事务(2PC/TC/C/Saga)④ 账本为什么用复式记账(借贷必平)⑤ Event Sourcing 让历史可重放(审计)⑥ 1M TPS 怎么落地(分区 + Raft + 本地文件)**。它最大的考点是**事务正确性 + 可审计性**——一道题考透分布式事务 + 复式记账 + 强一致存储。

> **本章和原书的区别**:原书把**三种方案演进(Redis 内存 → 关系库分布式事务 → Event Sourcing)、2PC/TC/C/Saga 对比、Event Sourcing + CQRS + Raft + 本地文件优化、可重放**讲得相当完整——Command/Event/State/状态机、Try-Confirm-Cancel、out-of-order 执行、Snapshot、最终设计是面试标准答案。但**全文默认"账户 = 一个余额数字"**,没严格化**复式记账**(资产=负债+权益、借贷必平、每笔至少两行)——而 2026 **TigerBeetle 就是专为复式记账设计的事务型 DB**(必讲);**没讲双花的多种防护手段**(乐观锁/悲观锁/DB 约束/分布式锁/UTXO);**没讲热点账户**(平台收款账户单点高频更新);**没讲读副本一致性**(钱包余额为什么不能读副本);**没讲 CBDC/数字人民币/M-Pesa** 规模;**没讲加密货币 UTXO 模型**对比;**没讲时序/时区结算**。本章补上。

## 1. 需求 + 估算

**澄清问题**(原书对话):

```mermaid
flowchart LR
    Q["数字钱包需求"] --> A["① 只做钱包间余额转账?<br/>(是)"]
    Q --> B["② 规模?(1M TPS)"]
    Q --> C["③ 事务保证够吗?(够)"]
    Q --> D["④ 要证明正确性?<br/>(可重放: 重放事件重建任意时刻余额)"]
    Q --> E["⑤ 可用性?(99.99%)"]
    Q --> F["⑥ 外汇?(不要)"]

    style Q fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style A fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style B fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style C fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style D fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style E fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style F fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
```

**功能(背)**:
- 钱包间余额转账(A 转 $1 给 C)。
- **1,000,000 TPS**。
- 可靠性 **99.99%**。
- 支持事务(原子性)。
- **支持可重放(reproducibility)**——能从最开头重放事件,重建任意时刻的余额。这是审计的核心。

**非功能**:强一致(钱不能多/少)、可审计、高可用、可扩展。

> 🪤 **追问陷阱(高频)**:"为什么要可重放?" → 审计员会问三个问题:**① 任意时刻账户余额是多少?② 历史和当前余额为什么是对的?③ 代码改了怎么证明逻辑还对?** 可重放(重放事件重建状态)能系统回答这三个问题——这是 Event Sourcing 的灵魂。

### 1.1 估算(背)

```
单关系库节点 ≈ 1000 TPS(TPC-E 基准)
目标 1M TPS → 需要 1000 节点

但每次转账 = 2 个账户操作(扣 A + 加 C)
→ 实际 2M TPS → 2000 节点 ⚠️

单节点 TPS 与节点数:
  100 TPS  → 20,000 节点
  1000 TPS → 2,000 节点
  10000 TPS → 200 节点 ⭐(提高单节点 TPS 是降本核心)
```

> 💡 **核心洞察**:**单节点 TPS 越高,总节点数越少 → 硬件成本越低**。所以设计目标之一是**提高单节点 TPS**(后面 Event Sourcing 用本地文件 + mmap 优化)。

## 2. API 设计

```
POST /v1/wallet/balance_transfer
{
  "from_account": "A",          // 借方账户(扣款)
  "to_account":   "C",          // 贷方账户(收款)
  "amount":       "1.00",       // 金额(用 string, 不用 double!)
  "currency":     "USD",        // ISO 4217
  "transaction_id": "01589980-2664-11ec-9621-0242ac130002"  // 幂等键
}

# 响应
{ "status": "success", "transaction_id": "01589980-..." }
```

> 🪤 **追问陷阱(高频)**:"amount 为什么是 string 不是 double?" → **浮点数有精度丢失**(0.1 + 0.2 ≠ 0.3)。金融场景必须 string + 整数分(cents)计算。**V2-Ch11 支付系统**讲过同样道理。**用 double 是经典 bug**——16 位有效数字后丢失,大额转账会少几分钱。

> 💡 **transaction_id 是幂等键**——客户端重试(网络抖动)用同一个 id,服务端去重,避免重复扣款(接 V2-Ch11 幂等)。

### 3.1 为什么这个方案不行 ⭐⭐⭐

```mermaid
flowchart LR
    TRANS["A 转 $1 给 C<br/>(A 在分片1, C 在分片2)"] --> S1["① 扣 A 分片1: -$1"]
    S1 --> CRASH["❌ 钱包服务在此崩溃"]
    CRASH --> S2["② 加 C 分片2: 没执行!"]
    S2 --> RESULT["$1 凭空消失"]

    style TRANS fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style S1 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style CRASH fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style S2 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style RESULT fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
```

> 🪤 **致命问题**:**两次更新没有原子性保证**。钱包服务在两次 Redis 更新之间崩溃 → **$1 凭空消失**(钱不能凭空消失,这是金融系统的红线)。**Redis 单节点事务跨不了节点**。需要**分布式事务**。

### 4.1 2PC(两阶段提交,底层方案)

```mermaid
sequenceDiagram
    participant C as 协调者(钱包服务)
    participant DA as 数据库A(账户A)
    participant DC as 数据库C(账户C)
    Note over C,DC: 阶段1: Prepare(锁定资源)
    C->>DA: prepare(扣$1)
    C->>DC: prepare(加$1)
    DA-->>C: yes(锁定)
    DC-->>C: yes(锁定)
    Note over C,DC: 阶段2: Commit(都yes才提交)
    C->>DA: commit
    C->>DC: commit
    DA-->>C: done
    DC-->>C: done
```

**2PC 流程**(背):
1. **阶段1 Prepare**:协调者(钱包服务)在多个数据库上正常读写(都**锁定**);准备提交时问所有库"能否提交?"。
2. **阶段2**:
   - 所有库回 "yes" → 协调者让所有库 **commit**;
   - 任一库回 "no" → 协调者让所有库 **abort**。

**2PC 的两个大问题**:

```mermaid
flowchart LR
    PC["2PC 问题"] --> P1["❌ 锁久<br/>(等其它节点消息时一直持锁)"]
    PC --> P2["❌ 协调者单点故障<br/>(挂了参与者一直锁定)"]
    P1 --> SLOW["性能差, 不适合高TPS"]
    P2 --> STUCK["参与者锁住, 需人工介入"]

    style PC fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style P1 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style P2 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style SLOW fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style STUCK fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
```

> 📝 **2PC 是底层方案**——`prepare` 步骤要数据库特殊支持(如 X/Open XA 标准)。**锁持有太久 + 协调者单点**是两大硬伤。

### 4.2 TC/C(Try-Confirm/Cancel,应用层补偿)⭐⭐⭐

```mermaid
flowchart LR
    TCC["TC/C 两阶段"] --> P1["阶段1 Try<br/>(各自预留/执行)"]
    TCC --> P2["阶段2<br/>(都成功→Confirm / 任一失败→Cancel)"]
    KEY["关键区别"] --> K1["2PC: 两阶段在同一事务内(锁住)"]
    KEY --> K2["TC/C: 每阶段是独立本地事务(已提交, 不锁)"]

    style TCC fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style P1 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style P2 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style KEY fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style K1 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style K2 fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
```

**TC/C 转账 $1 从 A 到 C 的例子**(背):

| 阶段 | 账户 A | 账户 C |
|------|--------|--------|
| 1. Try | 余额 -$1 | NOP(不动) |
| 2. Confirm(成功) | NOP(不动) | 余额 +$1 |
| 2. Cancel(失败) | 余额 +$1(回滚) | NOP |

**为什么这样设计?Try 阶段只动扣款方 A**(把 $1 真扣掉),C 不动。如果 Try 都成功 → Confirm 给 C 加 $1;如果 Try 任一失败 → Cancel 把 A 的 $1 加回去。

```mermaid
sequenceDiagram
    participant C as 协调者(钱包服务)
    participant DA as 数据库A(账户A)
    participant DC as 数据库C(账户C)
    Note over C,DC: Try 阶段(独立本地事务, 提交后解锁)
    C->>DA: 本地事务: A -$1(提交, 解锁)
    C->>DC: NOP(总是成功)
    DA-->>C: success
    DC-->>C: success
    Note over C,DC: Confirm 阶段(都成功)
    C->>DC: 本地事务: C +$1
    DC-->>C: success
```

**Try 阶段的三种选择**(只有一种有效):

| Try 阶段选择 | 账户 A | 账户 C | 是否有效 |
|------|--------|--------|------|
| 选择1 | -$1 | NOP | ✅ 有效 |
| 选择2 | NOP | +$1 | ❌ 无效 |
| 选择3 | -$1 | +$1 | ❌ 无效 |

- **选择2 无效**:Try 给 C +$1 成功了,但 A 失败 → Cancel 时别人可能已把 C 的 $1 转走,Cancel 扣 C 时余额不足。
- **选择3 无效**:并发给 A 和 C 都改,失败处理极复杂(A 加了 C 没扣怎么办?)。
- **只有选择1 有效**:**先扣款方,后收款方**。钱"先消失再出现",不会出现"先出现的钱被别人转走"。

> 📝 **核心结论**:**转账 = 先扣款方,后收款方**(扣款在 Try,收款在 Confirm)。这条规则贯穿 TC/C 和 Saga。

### 4.3 不平衡状态(Unbalanced Balance)⭐⭐

```mermaid
flowchart LR
    INIT["初始: A=$1, C=$0<br/>总和=$1"] --> TRY["Try 后: A=$0, C=$0<br/>总和=$0 ⚠️"]
    TRY -->|"违反会计基本规则<br/>(总和应不变)"| UNBAL["$1 凭空消失?"]
    UNBAL -->|"但 TC/C 保证最终一致<br/>(Confirm 后恢复)"| OK["Confirm 后: A=$0, C=$1<br/>总和=$1 ✅"]

    style INIT fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style TRY fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style UNBAL fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style OK fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
```

> 🪤 **追问陷阱(高频)**:"Try 阶段后 $1 哪去了?" → **Try 后 A=$0, C=$0,总和从 $1 变 $0,确实"不平衡"**——这违反会计基本规则(转账前后总和应不变)。但 **TC/C 是应用层事务,每阶段独立提交,中间状态对外可见但不影响最终一致**。Confirm 完成后恢复平衡。**这是 TC/C 与 2PC 的本质区别**:2PC 中间状态对外不可见(锁住),TC/C 中间状态对外可见。

### 4.5 乱序执行(Out-of-Order)⭐

```mermaid
sequenceDiagram
    participant C as 协调者
    participant DC as 数据库C(账户C)
    Note over C,DC: Try 给 C 是 NOP, 但网络延迟
    C->>DC: Try(NOP)
    Note over C: Try 失败(假设A失败), 进入Cancel
    C->>DC: Cancel(NOP)
    Note over DC: Cancel 先到!(网络乱序)
    DC-->>C: 没什么可Cancel的
    Note over DC: 留 out-of-order 标志
    DC-->>C: Try(NOP)迟到了
    Note over DC: Try 检查到标志, 直接返回失败
```

**乱序问题**:网络延迟导致 **Cancel 比 Try 先到**。处理:**每个节点允许在没收到 Try 时就 Cancel**(留 out-of-order 标志),后续迟到的 Try 检查到标志直接失败。这就是阶段状态表里 out-of-order 标志的用途。

### 4.6 Saga(线性补偿,微服务标配)⭐⭐

```mermaid
flowchart LR
    SAGA["Saga"] --> IDEA["所有操作排成序列<br/>每个是独立本地事务"]
    SAGA --> EXEC["顺序执行, 一个完成触发下一个"]
    SAGA --> ROLL["失败→逆序补偿回滚"]
    COORD["协调方式"] --> CH["① Choreography 编排<br/>(服务订阅事件, 去中心化)"]
    COORD --> OR["② Orchestration 编制 ⭐<br/>(单一协调者, 钱包首选)"]

    style SAGA fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style IDEA fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style EXEC fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style ROLL fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style COORD fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
```

**Saga 转账 $1 从 A 到 C**:
- 正常:`A-$1 → C+$1`(顺序执行)。
- 失败:如 `C+$1` 失败 → 逆序补偿 `C-$1`(撤销)→ `A+$1`(撤销)。

> 📝 **Choreography vs Orchestration**:Choreography(编排)各服务订阅事件,去中心化,但服务多了难管理;**Orchestration(编制)有单一协调者,复杂度可控**,**钱包系统首选 Orchestration**。

### 4.7 三种分布式事务对比(背)

| 维度 | 2PC | TC/C | Saga |
|------|-----|------|------|
| **层级** | 底层(DB 特殊支持) | 应用层(补偿) | 应用层(补偿) |
| **第一阶段** | 本地事务**未完成**(锁住) | 本地事务**已完成**(解锁) | 本地事务**已完成** |
| **第二阶段(成功)** | commit 所有本地事务 | 执行新本地事务(Confirm) | 触发下一个操作 |
| **第二阶段(失败)** | abort 所有本地事务 | 反向操作撤销(Cancel) | 逆序补偿回滚 |
| **执行顺序** | 任意 | 任意(可并行) | **线性** |
| **协调** | 协调者(单点) | 中央协调 | Orchestration(中央)/ Choreography(去中心) |
| **中间不一致对外可见** | 否(锁住) | 是 | 是 |
| **性能** | 差(锁久) | 好(可并行) | 中(线性) |

> 💡 **选型经验**:**无延迟要求 / 服务少** → Saga(微服务趋势);**延迟敏感 / 服务多** → TC/C(可并行)。**钱包转账只有 2 个操作,TC/C 和 Saga 都行**。

> 🪤 **追问陷阱**:"TC/C 和 Saga 最大区别?" → **执行顺序**:Saga 必须**线性**(一个完成才触发下一个);TC/C **可并行**(各 Try 独立)。延迟敏感场景 TC/C 更优。

## 5. 方案三:Event Sourcing ⭐⭐⭐⭐⭐(本章核心)


> 📝 **Event Sourcing 来自 DDD(领域驱动设计)**——一种能系统回答审计三问的设计哲学。**所有变更先存为不可变事件历史,数据库只是某一时刻的余额视图**。

### 5.1 四个核心术语

```mermaid

    ES["Event Sourcing 四术语"] --> CMD["① Command 命令<br/>(外界意图, 可能无效)"]
    ES --> EVT["② Event 事件<br/>(已验证的事实, 过去时)"]
    ES --> ST["③ State 状态<br/>(余额, 应用事件后变化)"]
    ES --> SM["④ State Machine 状态机<br/>(验证Command→生成Event, 应用Event→改State)"]

    style ES fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style CMD fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style EVT fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style ST fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style SM fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
```

| 术语 | 含义 | 钱包例子 |
|------|------|----------|
| **Command(命令)** | 外界意图,**可能无效** | "从 A 转 $1 到 C" |
| **Event(事件)** | 验证后的事实,**过去时, 确定性** | "A 被扣 $1"、"C 收到 $1" |
| **State(状态)** | 应用 Event 后的当前值 | 各账户余额(map: account→balance) |
| **State Machine(状态机)** | 验证 Command → 生成 Event;应用 Event → 改 State | 状态机逻辑**必须确定性**(无随机/无外部 IO) |

```mermaid

    SM1 -->|"余额够?"| EVT1["Event: A:-$1"]
    SM1 --> EVT2["Event: C:+$1"]
    EVT1 -->|"FIFO队列"| SM2["状态机2<br/>(应用)"]
    EVT2 --> SM2
    SM2 -->|"更新"| STATE[("State<br/>余额")]

    style CMD fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style SM1 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style EVT1 fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style EVT2 fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style SM2 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style STATE fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
```

**Command vs Event 关键区别**(背):
- Event **必须执行**(已验证的事实),用过去时;Command 是意图,可能失败。
- Command **可含随机/IO**;Event **必须确定性**(历史事实,同样输入永远同样输出)。
- 一个 Command 可生成 **0 到多个 Event**;Event 顺序必须遵循 Command 顺序。

**最终设计转账流程**(背,15 步精简):
1. 客户端发分布式事务给 Saga 协调者(含 2 操作:A-$1, C+$1)。
2. 协调者在阶段状态表建记录。
3. 协调者确定顺序,先发 `A-$1` 作 Command 给**分区1**(含账户A)。
4. 分区1 Raft Leader 收 Command → 存命令列表 → 验证 → 转 Event → Raft 复制 → 同步完成后执行 Event(扣 A)。
5. Event 同步后,CQRS 把数据同步到读路径,读路径重建状态。
6. 分区1 读路径把状态推回 Saga 协调者。
7. 协调者收到分区1 成功 → 阶段状态表记录。
8. 第一个操作成功 → 协调者执行第二个 `C+$1`,发 Command 给**分区2**(含账户C)。
9. 分区2 同样:Command → Event → Raft 复制 → 执行。
10. CQRS 同步读路径,推回协调者。
11. 协调者收到分区2 成功 → 阶段状态表记录。

### 9.1 复式记账(Double-Entry Bookkeeping)⭐⭐⭐⭐⭐(本章最硬核补丁)

原书把"账户 = 一个余额数字",但**真正的金融账户系统必须用复式记账**。

```mermaid
flowchart LR
    DBE["复式记账基本方程"] --> EQ["资产 = 负债 + 权益<br/>(Assets = Liabilities + Equity)"]
    DBE --> RULE["每笔交易借贷必平<br/>(Debit = Credit)"]
    DBE --> TWO["每笔至少2行<br/>(借方一行, 贷方一行)"]
    EX["A 转 $1 给 C"] --> ROW1["借: 现金(C) +$1"]
    EX --> ROW2["贷: 现金(A) -$1"]
    EX --> SUM["两行和 = 0 ✅(钱没凭空多/少)"]

    style DBE fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style EQ fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style RULE fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style TWO fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style EX fill:#FFE082,stroke:#F9A825,color:#1f1f1f

```

**复式记账** = 每笔交易记录为**至少两行**(借/贷),且**借贷必平**。

```mermaid
flowchart LR
    Q["为什么必须复式记账?"] --> A1["✅ 自动防错<br/>(借贷不平立即报错)"]

    Q --> A3["✅ 审计可追溯<br/>(每笔钱的来龙去脉)"]
    Q --> A4["✅ 防内部作恶<br/>(凭空造钱会破坏平衡)"]
    SINGLE["单余额方案❌"] --> BAD["余额被改无从发现<br/>(数据库 UPDATE balance=balance-1)"]

    style Q fill:#FFE082,stroke:#F9A825,color:#1f1f1f
```

> 🪤 **追问陷阱(高频)**:"钱包怎么防内部作恶 / 凭空造钱?" → **复式记账**:每笔交易借贷必平(Debit = Credit),全局所有账户余额之和 = 发行总额。**任何凭空造钱都会破坏平衡,审计一查就知道**。原书的"单余额方案"做不到这点(余额被改无从发现)。

**复式记账表结构(背)**:

```sql
-- 复式记账: 每笔交易 = 至少 2 行 entry(借/贷)
CREATE TABLE ledger_entry (
    entry_id      BIGINT PRIMARY KEY,         -- 全局唯一(单调递增)
    transaction_id UUID NOT NULL,             -- 同一交易的所有 entry 共享
    account_id    UUID NOT NULL,              -- 账户
    debit         NUMERIC(20,4) DEFAULT 0,    -- 借方金额
    credit        NUMERIC(20,4) DEFAULT 0,    -- 贷方金额
    created_at    TIMESTAMP NOT NULL,
    -- 约束: 每行必须 debit/credit 其一非零(不能空行)
    CONSTRAINT chk_nonzero CHECK (debit > 0 OR credit > 0),
    CONSTRAINT chk_xor CHECK ((debit > 0) != (credit > 0))
);
-- 全局校验: 每笔交易 SUM(debit) = SUM(credit)
```

### 9.3 双花防护的多种手段 ⭐⭐⭐(面试常问)

```mermaid
flowchart TD

    OPT --> O1["① 事务 + 行锁(悲观)<br/>SELECT FOR UPDATE"]
    OPT --> O2["② 乐观锁(版本号/CAS)<br/>UPDATE WHERE version=?"]
    OPT --> O3["③ DB 约束<br/>CHECK(balance >= 0)"]
    OPT --> O4["④ 复式记账借贷平衡"]

    OPT --> O6["⑥ 分布式锁(Redlock)"]

    style Q fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style OPT fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style O1 fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style O2 fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style O3 fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
```

| 手段 | 机制 | 优劣 |
|------|------|------|
| **悲观锁** | `SELECT FOR UPDATE` 锁账户行,事务完才释放 | 简单可靠;**热点账户锁争抢严重** |
| **乐观锁** | `UPDATE WHERE balance>=? AND version=?`(CAS) | 无锁高并发;失败要重试 |
| **DB 约束** | `CHECK(balance >= 0)` | 兜底防线;**MySQL 不强制 CHECK**(要用触发器) |
| **复式记账** | 借贷必平 + 余额非负 | 自动校验;需配合事务 |
| **UTXO 模型** | 每笔钱是独立未花费输出,花掉即标记 | 加密货币用;账户模型不用 |
| **分布式锁** | Redlock | **不推荐**(金融场景不如 DB 事务可靠) |

> 🪤 **追问陷阱(高频)**:"怎么防双花?" → **多种手段叠加**:**① 事务 + 行锁(悲观)或 CAS(乐观)② DB 约束余额非负兜底 ③ 复式记账借贷平衡自动校验**。分布式锁(Redlock)不推荐——金融场景 DB 事务比分布式锁可靠得多。

### 示例 1:复式记账转账(PostgreSQL + 事务 + 行锁防双花)

```sql
-- 复式记账: 一次转账 = 2 行 entry(借/贷), 单事务保证原子
BEGIN;

-- 悲观锁: 锁住两个账户行(防并发双花), 按ID排序防死锁
SELECT * FROM account WHERE id IN ('A', 'C') ORDER BY id FOR UPDATE;

-- 校验余额(A 必须 >= 1)
SELECT balance INTO v_a_balance FROM account WHERE id = 'A';
IF v_a_balance < 1 THEN
    ROLLBACK;
    RAISE 'insufficient balance';
END IF;

-- 写 2 行 entry(借贷必平)
INSERT INTO ledger_entry (entry_id, transaction_id, account_id, debit, credit)
VALUES
    (next_id(), 'txn-123', 'C', 1.00, 0),   -- 借: C 收款
    (next_id(), 'txn-123', 'A', 0,    1.00); -- 贷: A 扣款

-- 更新账户余额(派生数据, 也可从 entry 重算)
UPDATE account SET balance = balance - 1.00, version = version + 1
WHERE id = 'A' AND version = v_version;     -- 乐观锁兜底
UPDATE account SET balance = balance + 1.00, version = version + 1
WHERE id = 'C';

COMMIT;

-- 全局对账(每日): SUM(所有debit) = SUM(所有credit) → 借贷平衡
SELECT
    (SELECT SUM(debit) FROM ledger_entry WHERE created_at::date = '2026-07-08')
    =
    (SELECT SUM(credit) FROM ledger_entry WHERE created_at::date = '2026-07-08')
AS balanced;
```

### 示例 2:乐观锁(CAS)防双花(无锁高并发)

```python
def transfer_optimistic(from_id, to_id, amount, max_retry=3):
    """乐观锁: 读余额→计算新余额→CAS更新, 失败重试"""
    for attempt in range(max_retry):
        # 1. 读当前余额 + 版本号(无锁)
        a = db.query("SELECT balance, version FROM account WHERE id=?", from_id)
        if a.balance < amount:
            raise InsufficientBalance()
        # 2. CAS 更新(版本号匹配才成功)
        affected = db.execute(
            "UPDATE account SET balance=balance-?, version=version+1 "
            "WHERE id=? AND version=? AND balance>=?",
            amount, from_id, a.version, amount)
        if affected == 0:        # 并发冲突, 重试
            continue
        # 3. 收款方加钱
        db.execute("UPDATE account SET balance=balance+? WHERE id=?", amount, to_id)
        # 4. 写复式记账 entry
        db.execute("INSERT INTO ledger_entry ...")  # 借贷两行
        return "success"
    raise ConflictError("retry exhausted")
```

### 示例 3:TCC 分布式事务(Python 伪代码)

```python
def transfer_tcc(from_id, to_id, amount, txn_id):
    """TCC: Try(扣款方A) → Confirm(收款方C) / Cancel(回滚A)"""
    # 阶段状态表(随 A 的库存, 崩溃可恢复)
    phase = create_phase_status(txn_id, from_id, to_id, amount)

    try:
        # Try: 扣款方 A 真扣款(独立本地事务, 提交)
        tcc_try(from_id, -amount)    # A: balance -= amount
        phase.try_status_a = "success"
    except:
        phase.try_status_a = "failed"
        return "failed"

    try:
        # Try: 收款方 C 是 NOP(总是成功)
        tcc_try(to_id, 0)            # NOP
        phase.try_status_c = "success"
    except:
        # C 的 Try 失败 → Cancel: 把 A 的钱加回去
        phase.try_status_c = "failed"
        tcc_cancel(from_id, +amount)  # A: balance += amount(撤销)
        return "failed"

    # 全部 Try 成功 → Confirm: 给 C 加钱
    tcc_confirm(to_id, +amount)       # C: balance += amount
    phase.confirm_done = True
    return "success"
```

## 🪤 追问陷阱(面试官最爱问,本章集)

1. **"钱包为什么必须强一致?"** → 钱不能凭空多/少。**余额被并发扣超 = 双花**;**钱凭空消失 = 金融事故**。强一致是钱包红线。
2. **"单 Redis 方案为什么不行?"** → 两次更新(A 扣 + C 加)**不原子**。钱包服务在两次之间崩溃 → **$1 凭空消失**。Redis 单节点事务跨不了节点。
3. **"2PC 有什么问题?"** → **① 锁久**(等其它节点消息时一直持锁,性能差)**② 协调者单点故障**(挂了参与者一直锁定,需人工介入)。
4. **"TC/C 和 2PC 最大区别?"** → **2PC 两阶段在同一事务内(锁住),TC/C 每阶段是独立本地事务(已提交,不锁)**。TC/C 中间状态对外可见(不平衡),但最终一致。
5. **"TC/C 的 Try 阶段为什么只动扣款方 A?"** → **先扣款方,后收款方**。如果先给收款方加钱,Try 失败后 Cancel 时别人可能已把钱转走,余额不足无法撤销。
6. **"TC/C 和 Saga 最大区别?"** → **执行顺序**:Saga **线性**(一个完成才触发下一个);TC/C **可并行**(各 Try 独立)。延迟敏感场景 TC/C 更优。
7. **"Try 后 $1 哪去了?(不平衡状态)"** → Try 后 A=$0, C=$0,总和从 $1 变 $0。**违反会计规则但 TC/C 保证最终一致**(Confirm 后恢复)。这是 TC/C 与 2PC 的本质区别(中间状态对外可见)。
8. **"钱包服务重启 TC/C 进度丢了怎么办?"** → **阶段状态表**(存事务 ID/Try 各库状态/第二阶段名/out-of-order 标志),存在扣款方 A 的库。重启后从表读进度继续。
9. **"乱序执行怎么处理?"** → **Cancel 比 Try 先到**(网络乱序)。每个节点允许没收到 Try 就 Cancel(留 out-of-order 标志),迟到的 Try 检查到标志直接失败。
10. **"Event Sourcing 是什么?"** → 来自 DDD。**所有变更存为不可变事件历史,数据库只是某一时刻的余额视图**。Command(意图)→ 状态机验证 → Event(事实)→ 应用改 State。**状态机必须确定性**。
11. **"Event Sourcing 怎么回答审计三问?"** → **① 任意时刻余额 = 重放事件到该时刻 ② 余额正确性 = 从事件重算验证 ③ 代码改了 = 不同版本重放结果一致**。
12. **"Command 和 Event 区别?"** → Command 是意图(可含随机/IO,可能失败);Event 是已验证事实(**过去时,必须确定性**)。一个 Command 可生成 0~多个 Event。
13. **"为什么用 Raft?"** → 本地文件 = 单点故障。**只有 Event 需要高可靠**(Command 可重发,State/Snapshot 可从 Event 重建;Event 丢了永远丢)。Raft 多副本复制 Event,保证不丢 + 多节点顺序一致。
14. **"为什么 Event Sourcing 要本地文件 + mmap?"** → **免网络**(本地盘)+ **顺序写快**(append-only)+ **mmap 自动缓存**(append-only 几乎全在内存)。**顺序磁盘访问有时比随机内存还快**。
15. **"Snapshot 干什么?"** → 重放不必从头,从最近 Snapshot 续处理。**财务要求每天 00:00 快照核对当日交易**。存 HDFS(大二进制)。
16. **"amount 为什么是 string?"** → **浮点数精度丢失**(0.1+0.2≠0.3,16 位有效数字后丢)。金融必须 string + 整数分计算。**用 double 是经典 bug**。
17. **"怎么防双花?"** → **多手段叠加**:① 事务+行锁(悲观)或 CAS(乐观)② DB 约束余额非负兜底 ③ **复式记账借贷平衡自动校验**。分布式锁(Redlock)不推荐。
18. **"复式记账是什么?为什么要用?"** → **每笔交易借贷必平**(Debit=Credit),资产=负债+权益。**自动防错 + 全局余额恒等 + 审计可追溯 + 防凭空造钱**。原书"单余额方案"做不到(余额被改无从发现)。
19. **"热点账户怎么办?"** → 平台收款账户单行高频更新 → 锁争抢。**子账户拆分**(主账户拆 N 子账户负载均衡,查询合并)+ **异步累加**(写流水,余额定期合并)+ TigerBeetle(原生优化热点)。
20. **"钱包余额能读副本吗?"** → **不能!** 副本异步复制有延迟,刚转账完读副本读到旧余额 → read-your-writes 不成立 → 用户以为失败重试 → **双花**。**余额读走主库**,或带事务版本号。
21. **"TigerBeetle 是什么?"** → **2022 开源,专为金融账本设计的事务型 DB**。账户/转账/余额原生类型,内置借贷平衡校验,单节点百万 TPS,亚毫秒延迟,Viewstamped Replication 共识。**钱包 = TigerBeetle 原生模型**。
22. **"UTXO 和账户模型区别?"** → 账户模型(支付宝/银行):账户=一个余额,双花要锁/事务;**UTXO(比特币):钱=一组未花费输出,花掉即标记,天然防双花**。钱包系统一般用账户模型。
23. **"1M TPS 怎么落地?"** → **分区**(hash 分区)+ 每分区 Raft 组(Event Sourcing)+ 跨分区 Saga/TC/C + 本地文件(mmap/RocksDB)+ Snapshot。**TigerBeetle 单节点百万 TPS 可大幅减少节点数**。
24. **"数字人民币和支付宝区别?"** → **数字人民币是 CBDC**(央行数字货币,央行直发,双层运营,双离线 NFC,可控匿名);支付宝是商业银行存款货币(商业银行运营)。**M-Pesa 是肯尼亚移动钱包**(无银行账户人群)。

**核心 Takeaways**:

1. **钱包是金融级强一致系统**——钱不能凭空多/少。**单 Redis 方案不行**(两次更新不原子,中间崩溃钱凭空消失)。
2. **分布式事务三方案**:**2PC**(底层,锁久+协调者单点)/ **TC/C**(应用层补偿,可并行)/ **Saga**(线性补偿,微服务标配)。**转账铁律:先扣款方,后收款方**。
3. **TC/C 中间状态对外可见但不影响最终一致**(不平衡状态:Try 后 $1 暂时"消失",Confirm 后恢复)。**这是 TC/C 与 2PC 的本质区别**。
4. **阶段状态表存事务进度**(崩溃可恢复)+ **out-of-order 标志**处理 Cancel 比 Try 先到的乱序。
5. **Event Sourcing 是钱包的事实标准**——Command(意图)→ 状态机验证 → Event(不可变事实)→ 应用改 State。**状态机必须确定性**。**可重放**系统回答审计三问。
6. **Event Sourcing 高性能**:本地文件(append-only + mmap)+ State 用 RocksDB(LSM)+ Snapshot 加速重放。
7. **可靠性靠 Raft**——只有 Event 需高可靠(Command 可重发,State/Snapshot 可重建)。Raft 多副本复制 Event,多数节点在线即可工作。
8. **CQRS**:写路径 1 个状态机,读路径多个只读状态机重建不同视图(余额/流水/对账)。**Push 模型**(反向代理 + 只读状态机主动推)实现实时体验。
9. **跨分区复用 Saga/TC/C**——每分区 Raft 组(Event Sourcing),协调者按 Saga 顺序触发各分区。
10. **复式记账(2026 补)**:借贷必平(Debit=Credit),资产=负债+权益。**自动防错 + 全局余额恒等 + 防凭空造钱**。原书"单余额方案"做不到。
11. **TigerBeetle(2026 补)**:专为金融账本设计的事务型 DB,账户/转账原生类型,百万 TPS 单节点,亚毫秒延迟。**钱包 = TigerBeetle 原生模型**。
12. **双花防护多手段**:事务+行锁(悲观)/ CAS(乐观)/ DB 约束余额非负/复式记账借贷平衡。**分布式锁不推荐**。
13. **热点账户**(平台收款账户):子账户拆分 + 异步累加 + TigerBeetle。
14. **钱包余额不能读副本**——异步复制延迟致 read-your-writes 不成立 → 重试致双花。**余额读走主库**。
15. **UTXO 模型**(比特币)vs **账户模型**(支付宝/银行/TigerBeetle)——加密货币用 UTXO(天然防双花),钱包系统用账户模型。**CBDC(数字人民币/M-Pesa)是 2026 全球实践**。

> 🔗 **连接上下章**:**V2-Ch11 支付系统**是交易链路(下单→支付→回调);**V2-Ch12 数字钱包**是**底层账户系统**(账户余额/流水/复式记账/双花/强一致),把支付学的强一致深化到账户级。**V2-Ch13 证券交易**把强一致 + 低延迟推到极致(撮合引擎/FPGA/订单簿/µs 级)。**金融三件套:支付/钱包/证券——钱包是三者的地基**。
