# Volume 2 · Chapter 10: 设计实时游戏排行榜 (Design a Real-time Gaming Leaderboard)

> 📑 **导航**:[← 对象存储](ch2_09-设计对象存储.md) · [📚 总目录](../README.md) · [支付 →](ch2_11-设计支付系统.md)
> 🔗 **相关**:[缓存](../SDA/aws_04-缓存策略与机制.md) · [AWS存储](../SDA/aws_10-AWS存储服务.md)


> **本章定位**:排行榜是**"海量高频更新 + 实时有序排名"**的内存计算题——它是手游锦标赛/积分系统的设计骨架。它把 Vol.1 的哈希一致性、Vol.2 Ch2 的有状态服务全用上。灵魂是六件事:**① 为什么要服务端设分(防作弊)② 关系库为什么不行(ORDER BY 全表 O(n))③ Redis ZSET(跳表)为什么是银弹(O(log n))④ 怎么取 Top10 / 个人排名 / 前后 ±4 ⑤ 怎么扩展(500M DAU 分片:固定分区 vs 哈希分区)⑥ 平局打破 + 故障恢复**。它最大的考点是**数据结构选型**——一道题考透跳表 + 有序集合。

> **本章和原书的区别**:原书把**关系库方案为什么不行、Redis ZSET 工作流、跳表原理、固定/哈希分区、NoSQL 替代、平局打破**讲得相当完整——ZADD/ZINCRBY/ZREVRANGE/ZREVRANK、650MB 内存估算、scatter-gather、DynamoDB write sharding、percentile 都覆盖,是面试标准答案。但**全文是"内存数独"思维,默认单 Redis 撑 5M DAU**——而 **2026 超大规模(亿级玩家)需要更激进的方案**(lookup table O(1) 排名、tier 分层);**没提 DragonflyDB**(多线程 Redis 替代,吞吐 25×);**没提 AWS MemoryDB**(持久化 Redis 当主库);**没提 CRDT 跨区排行榜**;**percentile 用 cron 离线算**——而 2026 用 **t-digest 流式近似**;**没提 Redis 7 listpack**(替代 ziplist,小集合省内存);**实时推送客户端拉取**(GET 轮询)——而 2026 用 **WebSocket/SSE 推送**。本章补上。

**澄清问题**(原书对话):

```mermaid

    Q --> F["⑥ 同分怎么排?<br/>(同排名, 加分点讲打破)"]

    style Q fill:#FFE082,stroke:#F9A825,color:#1f1f1f

    style F fill:#80DEEA,stroke:#0097A7,color:#1f1f1f

```

**功能**:① 显 Top10;② 显用户个人排名;③ 显某用户前后 ±4(加分项)。

**非功能性**:**实时更新分数**(写入即时反映到榜);可扩展;可用;可靠。

**估算**(背):

```
5M DAU / 10^5s = 50 用户/s(均匀)
峰值 5× = 250 用户/s
分数更新 QPS = 50 × 10局/天 = 500, 峰值 2500
Top10 获取 QPS ≈ 50(开游戏时拉一次)
存储: 25M MAU 最坏每人入榜
  每条 = 24B(user_id) + 2B(score) = 26B
  25M × 26B = 650MB(翻倍算跳表/hash开销 → ~1.3GB)
→ 单 Redis 撑得住(内存 + 2500 QPS 都够)
```

> 💡 **核心洞察**:**5M DAU 规模,单 Redis 完全够**(650MB 内存,2500 QPS)。**只有到 500M DAU 才需分片**。

### 3.2 方案一:关系库(❌ 不行)⭐⭐⭐

```mermaid
flowchart LR
    RDS["关系库方案"] --> T["leaderboard 表<br/>(user_id, score)"]

    RANK --> SLOW["❌ 百万行排名要10秒+<br/>不可接受"]
    PROB["为什么不行"] --> P1["每次都要排全部到正确位"]
    PROB --> P2["数据持续变→缓存不可行"]
    PROB --> P3["非榜首用户的排名难求"]

    style RDS fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style T fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style UP fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style RANK fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style SLOW fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style PROB fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style P1 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style P2 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style P3 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
```

> 📝 **关系库方案**:leaderboard 表,赢一局 `UPDATE score=score+1`;排名 `SELECT ... ORDER BY score DESC`。**问题**:
> - 排名要排全部玩家到正确位(可能同分)→ **百万行要 10 秒+**;
> - 数据**持续变化** → 缓存不可行;
> - **非榜首用户排名难求**(要嵌套子查询 `COUNT(*) WHERE score>=`)。

```sql
-- 关系库求排名(嵌套查询, 慢)
SELECT *, (SELECT COUNT(*) FROM leaderboard lb2
           WHERE lb2.score >= lb1.score) AS rank
FROM leaderboard lb1
WHERE lb1.user_id = ?;
-- LIMIT 10 只解 Top10, 个人排名仍要全表扫
```

### 3.4 跳表原理 ⭐⭐(面试常问)

```mermaid
flowchart LR
    SKIP["跳表 Skip List"] --> BASE["底层: 排序链表 O(n)"]
    SKIP --> IDX["加速: 多级索引"]
    IDX --> L1["L1: 每隔1个跳"]
    IDX --> L2["L2: 每隔2个跳(L1的)"]
    IDX --> LX["Lx: 跳到中间附近"]
    EFF["效果"] --> E1["5级索引: 62节点→11节点"]
    EFF --> LOG2["查找 O(log n)<br/>(类比二分, 但链表上)"]

    style SKIP fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style BASE fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style IDX fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style L1 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style L2 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style LX fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style EFF fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style E1 fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style LOG2 fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
```

> 📝 **跳表** = 排序链表 + 多级索引(类比链表上的二分)。底层 O(n),加 L1(每隔一个跳)/L2/.../Lx 索引 → 查找 **O(log n)**。例 5 级索引,从底层走 62 节点 → 跳表只走 11 节点。**每次插入/更新自动放到正确位**(关系库要重排)。

## 4. ZSET 工作流 ⭐⭐⭐⭐⭐

```mermaid
flowchart LR
    OP["Redis 命令"] --> ZADD["ZADD<br/>插入或更新(O(log n))"]
    OP --> ZIN["ZINCRBY ⭐<br/>分数增(O(log n))"]
    OP --> ZRANGE["ZREVRANGE<br/>取Top-N范围(O(log n+m))"]
    OP --> ZRANK["ZREVRANK<br/>取个人排名(O(log n))"]

    style OP fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style ZADD fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style ZIN fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style ZRANGE fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style ZRANK fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
```

| 命令 | 用途 | 复杂度 |
|------|------|--------|
| **ZADD** | 不存在则插入,存在则更新分数 | O(log n) |
| **ZINCRBY** ⭐ | 分数增(不存在则从 0 起) | O(log n) |
| **ZREVRANGE** | 降序取范围(Top-N)+ WITHSCORES | O(log n + m) |
| **ZREVRANK** | 取个人排名(降序) | O(log n) |

### 4.1 四个核心操作

```mermaid
flowchart LR
    W1["① 用户得分"] --> C1["ZINCRBY leaderboard_feb 1 'mary1934'"]
    W2["② 取 Top10"] --> C2["ZREVRANGE leaderboard_feb 0 9 WITHSCORES"]
    W3["③ 取个人排名"] --> C3["ZREVRANK leaderboard_feb 'mary1934'"]
    W4["④ 取前后±4<br/>(rank=361)"] --> C4["ZREVRANGE leaderboard_feb 357 365"]

    style W1 fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style C1 fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style W2 fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style C2 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style W3 fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style C3 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style W4 fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style C4 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
```

- **得分**:`ZINCRBY leaderboard_feb_2021 1 'mary1934'`(赢一局 +1)。
- **取 Top10**:`ZREVRANGE leaderboard_feb_2021 0 9 WITHSCORES`(降序 0-9 + 带分数)。
- **个人排名**:`ZREVRANK leaderboard_feb_2021 'mary1934'`。
- **前后 ±4**:先 `ZREVRANK` 拿到 rank=361,再 `ZREVRANGE 357 365`(前后各 4)。

> 💡 **每月新建一个 ZSET**(`leaderboard_<月>`),旧的转历史存储。

### 示例 3:固定分区(分数段)分片

```python
def shard_for_score(score, shards=10, per_shard=100):
    return min(score // per_shard, shards - 1)     # 分数→分片

def get_top10(shards):
    # Top10 在最高分片
    return redis.zrevrange(f'lb_2026_07_{shards-1}', 0, 9, withscores=True)

def get_rank(user_id, score, shards):
    local_rank = redis.zrevrank(f'lb_2026_07_{shard_for_score(score)}', user_id)
    # 排名 = 本地rank + 更高分片总人数
    higher = sum(redis.zcard(f'lb_2026_07_{s}')      # INFO keyspace O(1)
                 for s in range(shard_for_score(score)+1, shards))
    return local_rank + higher
```

### 示例 4:lookup table O(1) 精确排名(2026 增量)

```python
# 分数有界(0-10000): 用计数数组 + 前缀和做 O(1) 精确排名
def update_score(user_id, new_score):
    redis.hset('score_of', user_id, new_score)      # user→当前分
    redis.hincrby('count_at', new_score, 1)         # 该分数人数+1

def get_rank(user_id):
    score = int(redis.hget('score_of', user_id))
    # 排名 = 所有更高分数的人数累加(前缀和, 可预计算缓存)
    higher = sum(int(redis.hget('count_at', s) or 0)
                 for s in range(score+1, 10001))
    return higher + 1                               # O(分数范围), 可用BIT优化到O(log)
```

## 🪤 追问陷阱(面试官最爱问,本章集)

1. **"分数为什么不能客户端设?"** → 客户端设分会被 **MITM 中间人攻击**(挂代理改分)。**服务端设分**:游戏服务校验输赢 → 调排行榜服务。
2. **"关系库为什么不行?"** → `ORDER BY score DESC` 排全部百万行 **10 秒+**;数据持续变缓存不可行;非榜首排名要嵌套子查询全表扫。
3. **"用什么数据结构?"** → **Redis ZSET(有序集合)** = hash 表 + 跳表;增删查 O(log n),范围查 O(log n+m)。**为排行榜而生**。
4. **"跳表是什么?"** → 排序链表 + 多级索引(链表上的二分);底层 O(n) → 加索引 O(log n);**插入自动放正确位**(关系库要重排)。
5. **"取 Top10 怎么做?"** → `ZREVRANGE leaderboard_<月> 0 9 WITHSCORES`(降序 + 带分数)。
6. **"取个人排名怎么做?"** → `ZREVRANK leaderboard_<月> user_id`(O(log n))。
7. **"取前后 ±4 怎么做?"** → 先 `ZREVRANK` 拿 rank,再 `ZREVRANGE rank-4 rank+4`。
8. **"单 Redis 够吗?"** → 5M DAU:650MB 内存(×2 算开销 1.3GB)+ 2500 QPS,**单 Redis 撑得住**。500M DAU 才需分片。
9. **"持久化怎么做?"** → Redis 持久化(重启慢)→ **读副本 failover**;配套 MySQL 存 point(带时间戳),**全挂可重建**。
10. **"500M DAU 怎么分片?"** → **固定分区(按分数段)**:Top10 从最高分片取;个人排名 = 本地 rank + 更高分片总人数(分片人数 O(1) 取)。哈希分区 Top10/排名都难,不如固定。
11. **"哈希分区为什么不如固定分区?"** → 哈希分区 Top10 要 scatter-gather(慢);个人排名难求;等最慢分片延迟高。
12. **"同分怎么排?"** → 用 Redis Hash 存 `user→最近赢局时间戳`,同分时**先达成者排前**。
13. **"Redis 全挂怎么办?"** → 从 MySQL 遍历每条赢局记录(带时间戳),逐个 `ZINCRBY` 重建榜单(离线脚本)。
14. **"大规模个人排名太贵怎么办?"** → 用 **percentile**(百分位,"前 10-20%"比"第 1,200,001"友好);2026 用 **lookup table**(分数有界时 O(1) 精确排名)或 **t-digest**(流式近似)。
15. **"要不要 MQ?"** → 分数仅用于排行榜不用;分数还用于分析/推送/多人通知 → 用 Kafka 多消费者。回合制游戏需通知其他玩家分数 → 用 MQ。
16. **"2026 超大规模怎么搞?"** → **DragonflyDB**(多线程 25× 吞吐)+ **lookup table**(O(1) 精确排名)+ **分层**(Top-N 热层 Redis,其余冷层 percentile)+ **MemoryDB**(持久化免重建)。

**核心 Takeaways**:

1. **排行榜的核心是数据结构选型**——关系库 `ORDER BY` 全表 O(n) 不行;**Redis ZSET(跳表)O(log n)** 是银弹。
2. **服务端设分防作弊**——客户端设分会被 MITM 攻击;游戏服务校验输赢 → 调排行榜服务。
3. **Redis ZSET = hash 表 + 跳表**:ZINCRBY 得分;ZREVRANGE 取 Top10;ZREVRANK 个人排名;ZREVRANGE 取前后 ±4。
4. **5M DAU 单 Redis 够**(650MB 内存,2500 QPS);持久化用读副本 failover + MySQL 存 point 供重建。
5. **500M DAU 分片**:**固定分区(按分数段)** 优于哈希分区——Top10 从最高分片取,个人排名 = 本地 rank + 更高分片总人数。
6. **percentile 比精确排名友好**——"前 10-20%" 比"第 1,200,001"体验好;cron 离线算分位数→score 映射。
7. **平局打破**:Hash 存 `user→时间戳`,同分先达成者排前;**故障恢复**:从 MySQL 遍历赢局重建。
8. **2026 lookup table**:分数有界时,计数数组 + 前缀和做 **O(1) 精确排名**(Discord/Reddit 实践),无需 scatter-gather。
9. **DragonflyDB**(多线程 25× Redis)+ **MemoryDB**(持久化免重建)+ **WebSocket 推送**(替代轮询)+ **t-digest**(流式 percentile)+ **分层**(热 Redis/冷 percentile)。
10. **从零建推荐 serverless**(API Gateway + Lambda,免运维自动扩缩)。

**Lambda 函数示例(分数提交 → ZADD + DynamoDB)**:

```python
import boto3, json, os
redis = boto3.client('elasticache')  # 实际用 redis-py 连 ElastiCache endpoint
dynamodb = boto3.resource('dynamodb')
sqs = boto3.client('sqs')
score_table = dynamodb.Table('PlayerScores')
LB_KEY = os.environ['LEADERBOARD_KEY']  # 如 leaderboard_2026_07

def submit_score_handler(event, context):
    """API Gateway 触发: 玩家提交分数"""
    body = json.loads(event['body'])
    user_id, points = body['user_id'], body['points']
    # ① Redis ZSET 增分(跳表 O(log n))
    redis.zincrby(LB_KEY, points, user_id)
    # ② DynamoDB 落档(持久化, 供重建/分析)
    score_table.put_item(Item={
        'player_id': user_id,
        'timestamp': int(event['requestContext']['requestTimeEpoch']),
        'score': points, 'region': body.get('region', 'global'),
    })
    # ③ SQS 异步触发排名更新/通知
    sqs.send_message(QueueUrl=os.environ['QUEUE_URL'], MessageBody=json.dumps({'user_id': user_id}))
    return {'statusCode': 200, 'body': json.dumps({'status': 'ok'})}
```

> 📝 **三件套逻辑**(原书 Flow 17-3):① ZADD/ZINCRBY 写 Redis ZSET(实时榜);② put_item 落 DynamoDB(持久化);③ SQS 解耦排名更新/通知(削峰)。**Lambda 是无状态的,状态全在 Redis + DynamoDB**。

**SDE 分区方案在 AWS 上的落地**:

| SDE 设计 | AWS 落地 | 备注 |
|---------|---------|------|
| **固定分区(分数段)** | ElastiCache 多个 key:`lb_<月>_0`~`_9`,按分数段路由 | SDE §7.2;Top10 从最高 key 取 |
| **哈希分区(scatter-gather)** | ElastiCache **Cluster mode**(CRC16 % 16384 自动分片) | SDE §7.3;Top10 用 scatter-gather |
| **个人排名(percentile)** | DynamoDB write sharding + GSI(详见 SDE §8) | 超大规模精确排名太贵 |
| **冷热分离** | Top-N 留 Redis(热),全量/历史存 DynamoDB(冷) | 亿级玩家必备 |

**ElastiCache Cluster mode 关键点**(原书书页 851-852):
- **多分片**:数据散到多节点,扩容加 shard 即可(原书:"Redis cluster mode, allowing the cluster to store more data and handle higher throughput")。
- **副本 + 自动 failover**:每分片主 + 从,主挂提升从(原书:"enhances the fault tolerance via automatic failovers to replicas")。
- **Global Datastore**:跨 Region 复制缓存(对应 DynamoDB Global Tables)。

**CloudFront 缓存榜单**(原书书页 863):榜单是"读多写少 + 可短暂过期"——**CloudFront 缓存 `GET /scores` 几秒 TTL**,全球用户就近命中边缘,Redis 读 QPS骤降。这是分层缓存的一环(原书:"hierarchical caching that includes ... edge caching with services like Amazon CloudFront")。

> 🪤 **追问陷阱**:"CloudFront 缓存榜单会不会让玩家看到旧分?" → **几秒 TTL 是可接受的最终一致**(玩家容忍 2-3 秒延迟看到新分,但不容忍 10 秒+)。**个人排名查询不缓存**(走 Redis ZRANK 实时)。

**Day N 关键升级**(原书书页 850-864):

1. **ElastiCache 集群分片 + 副本**:Redis Cluster mode,每分片主+从,主挂自动 failover 到副本(原书:"primary-secondary setup to handle large leaderboard sorted sets")。**主服务"reads your write"一致性**(粘性会话),从副本异步复制(最终一致)。

2. **DynamoDB Global Tables 跨 Region**:玩家数据多区 active-active,任一区可写,自动复制(对应 SDE §10.3 提的 CRDT 跨区思路,但 DynamoDB 用 LWW 合并)。**RPO≈0,低延迟就近读**。

3. **Kinesis 实时分数变更流**(原书用 SQS,Day N 升级):分数提交 → **Kinesis Data Streams** → Lambda/Flink 消费 → 批量更新 Redis/DynamoDB。比 SQS 更适合**高吞吐 + 多消费者**(分析/通知/榜单同时消费)。详见 `aws_12`。

4. **冷热榜分离**:
   - **实时榜(Redis)**:只存 Top-N(如 Top 10000)的 ZSET,亚毫秒读。
   - **历史/全量榜(DynamoDB)**:全部玩家分数 + 历史归档(S3 Glacier,原书书页 826)。查询非 Top-N 走 DynamoDB + percentile 近似。

5. **AppSync push 替代 pull**(原书书页 852):原书明确说"push the data from the server to the user devices instead of all the user devices pulling"——用 **AppSync managed GraphQL + WebSocket** 推 Top10 变化给客户端,避免轮询。

6. **监控**:CloudWatch 监 CPU/内存/错误率/延迟,X-Ray 分布式链路追踪(对应 SDA Ch1 的可观测四支柱)。

### 💰 成本与性能

**ElastiCache 内存占用估算**(沿用 SDE §5):
- 25M MAU × 26B = **650MB**(纯数据)
- ×2(跳表 + hash 开销)≈ **1.3GB**
- 选 cache.r6g.large(约 13GB 内存)绑绑有余,Day 0 甚至可用 cache.t4g.small。

**DynamoDB on-demand 成本**(原书书页 855 算例,10M 玩家):
- 存储 750GB × $0.25 = **$187.5/月**
- 写(167 TPS)= **$548.6/月**
- 读(231 TPS)= **$75.88/月**
- **合计 ~$812/月**(未含备份/Streams/GSI)

**API Gateway 成本**(原书书页 856):167 写 TPS ≈ 4.38 亿请求/月,**$1462/月**。

**省钱杠杆**:

| 杠杆 | 节省 | 代价 |
|------|------|------|
| **CloudFront 缓存榜单** | 读 Redis QPS 骤降(榜单是热点) | 几秒 TTL 的最终一致 |
| **DynamoDB provisioned + autoscale** | 比 on-demand 便宜(稳态流量) | 容量预估负担 |
| **冷热分离** | Redis 只存 Top-N,内存省 10× | 全量查询变慢 |
| **Lambda 按调用付费** | 低峰自动归零 | 冷启动(用 provisioned concurrency 解) |

> 💡 **TCO 视角**(原书书页 852-859):原书强调别只看云账单——还要算**初始成本(DevOps 工程师)/ 运维成本(监控/升级)/ 维护成本(技术债)/ 退役成本(迁移)**。**托管服务(Lambda/DynamoDB/ElastiCache)的真正价值是降运维人头,不是降单价**。
