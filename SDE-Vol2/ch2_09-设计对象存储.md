# Volume 2 · Chapter 9: 设计对象存储 (Design an S3-like Object Storage)

> 📑 **导航**:[← 邮件服务](ch2_08-设计分布式邮件服务.md) · [📚 总目录](../README.md) · [排行榜 →](ch2_10-设计游戏排行榜.md)
> 🔗 **相关**:[YouTube](../SDE-Vol1/ch1_14-设计YouTube.md) · [Drive](../SDE-Vol1/ch1_15-设计GoogleDrive.md) · [AWS存储](../SDA/aws_10-AWS存储服务.md)


> **本章定位**:对象存储是**"海量不可变数据 + 极致持久性 + 低成本"**的基础设施题——它是 AWS S3 的设计骨架。它把 Vol.1 Ch6 的存储引擎(LSM/B+树)、Vol.1 Ch5 的哈希一致性、Vol.2 Ch4 的一致性协议全用上。灵魂是六件事:**① 元数据和数据分离(inode 思想)② 小对象合并成大文件(WAL 思想)③ 持久性靠多副本/纠删码(6-11 个 9)④ 失败域隔离(机架/AZ)⑤ 数据校验(checksum)⑥ 海量元数据分片**。它是少有的"CAP 里宁可牺牲性能也要耐久性和成本"的系统——为冷数据而生。

> **本章和原书的区别**:原书把**对象存储的高层架构、数据节点小对象合并、元数据分片、版本化、multipart、垃圾回收 compaction**讲得相当完整——存储 101、bucket/object 概念、6 个 9 持久性、3 副本 vs 纠删码、checksum、SQLite 存 object_mapping,都覆盖,是面试标准答案。但**主用 3 副本(说纠删码"复杂度高")**——而 **2026 真实 S3 主力是纠删码**(成本和 11 个 9 持久性碾压);**checksum 用 MD5**——而 **S3 自 2022 起支持 CRC32/CRC32C/SHA-1/SHA-256,MD5 已弱**;**没提 Facebook Haystack/f4**(本题的设计原型论文);**没提强一致**——而 **S3 2020.12 起默认强一致(read-after-write)**,原书还在说"最终一致是可接受的";**没提分级存储**(Glacier 冷存/Intelligent-Tiering);**没提 S3 Select / Object Lambda / S3 Tables**。本章补上。

## 1. 需求 + 估算

**澄清问题**(原书对话):

```mermaid
flowchart LR
    Q["对象存储需求"] --> A["① 功能?<br/>(建桶/上传下载/版本化/list)"]
    Q --> B["② 数据大小?<br/>(KB级~GB级都要)"]
    Q --> C["③ 规模?<br/>(100PB/年)"]
    Q --> D["④ SLA?<br/>(耐久6个9, 可用4个9)"]

    style Q fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style A fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style B fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style C fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style D fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
```

**功能**:建桶 / 上传下载对象 / 版本化 / 列桶内对象(类似 `aws s3 ls`)。

**非功能性**:**100PB 数据**;耐久 **6 个 9(99.9999%)**;可用 **4 个 9(99.99%)**;**存储效率**(降本同时高可靠)。

**估算**(背):

```
对象大小分布: 20%小(<1MB), 60%中(1~64MB), 20%大(>64MB)
取中位数: 0.5MB / 32MB / 200MB, 40%存储利用率
100PB = 10^11 MB
对象总数 = (10^11 × 0.4) / (0.2×0.5 + 0.6×32 + 0.2×200) = 0.68 亿
元数据(每对象1KB) = 0.68 TB
单盘 SATA 7200rpm: 100~150 IOPS
→ 数据节点合并小对象(降IOPS), 元数据分片(0.68TB超单机)
```

> 💡 **核心洞察**:**小对象是 IOPS 杀手**——百万级小文件浪费盘块 + 耗尽 inode。**必须合并成大文件**。

## 2. 存储 101:Block / File / Object ⭐⭐⭐⭐⭐

```mermaid
flowchart LR
    ST["存储系统"] --> BLK["块存储 Block<br/>(1960s, HDD/SSD, 原始块)"]
    ST --> FIL["文件存储 File<br/>(建在块上, 目录树)"]
    ST --> OBJ["对象存储 Object ⭐<br/>(不可变, REST, 海量冷数据)"]

    style ST fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style BLK fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style FIL fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style OBJ fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
```

| 维度 | 块存储 | 文件存储 | **对象存储** ⭐ |
|------|--------|---------|----------------|
| **可变性** | 可变 | 可变 | **不可变**(版本化,无原地更新) |
| **成本** | 高 | 中高 | **低** |
| **性能** | 中高/极高 | 中高 | **低-中** |
| **一致性** | 强 | 强 | **强**(2020 起) |
| **访问** | SAS/iSCSI/FC | NFS/CIFS/SMB | **RESTful API** |
| **可扩展** | 中 | 高 | **海量** |
| **适用** | VM、数据库、高性能应用 | 通用文件共享 | **二进制/非结构化冷数据** |

> 📝 **对象存储的"刻意取舍"**:**牺牲性能换极高耐久 + 海量 + 低成本**。面向"冷数据"(归档/备份/图片视频),不面向热数据库。

**核心术语**:
- **Bucket(桶)**:逻辑容器,**桶名全局唯一**;上传对象前必须先建桶。
- **Object(对象)**:= 数据(payload)+ 元数据(name-value 对)。
- **Versioning(版本化)**:桶级开关,保留多版本(防误删/覆盖)。
- **URI**:资源唯一标识(RESTful 访问)。
- **SLA**:例 S3 Standard-IA,**11 个 9 耐久**(跨多 AZ),**99.9% 可用**。

## 4. 数据存储设计 ⭐⭐⭐⭐⭐(本章难点)

数据存储 = **数据路由服务 + 放置服务 + 数据节点**。

### 4.1 三大组件

```mermaid
flowchart TB
    DS["数据存储"] --> DRS["数据路由服务<br/>(无状态, gRPC)"]
    DS --> PL["放置服务 ⭐<br/>(虚拟集群图, Raft/Paxos)"]
    DS --> DN["数据节点<br/>(副本组)"]
    DRS -->|查最佳节点| PL
    DRS -->|读写| DN

    style DS fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style DRS fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style PL fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style DN fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
```

| 组件 | 职责 |
|------|------|
| **数据路由服务** | 无状态;查放置服务选节点;读写数据节点 |
| **放置服务** ⭐ | 维护**虚拟集群图**(物理拓扑);心跳 15s 监控;**5-7 节点 Raft/Paxos**(多数派存活即工作) |
| **数据节点** | 存数据;复制到副本组(replication group) |

> 📝 **放置服务是核心**:它用虚拟集群图确保**副本物理隔离**(不同机架/AZ)——这是高耐久的关键。5-7 节点 + Raft/Paxos 容错(7 节点容忍 3 故障)。

### 4.2 数据持久流程(5 步)

```mermaid
sequenceDiagram
    participant API as API服务
    participant DRS as 数据路由服务
    participant PL as 放置服务
    participant P as 主数据节点
    participant S1 as 副本1
    participant S2 as 副本2
    API->>DRS: 转发对象数据
    DRS->>PL: 查放置(查虚拟集群图)
    PL-->>DRS: 返回主节点
    DRS->>P: 发数据+UUID
    P->>P: 本地保存
    P->>S1: 复制
    P->>S2: 复制
    S1-->>P: 成功
    S2-->>P: 成功
    P-->>DRS: 全副本确认
    DRS-->>API: 返回 UUID
```

- **步骤 2**:放置服务用**一致性哈希**(接 Vol.1 Ch5)返回副本组——**确定性 + 抗增删节点**。
- **步骤 4**:主节点**等所有副本确认才返回** → 强一致(但延迟高,等最慢副本)。

```mermaid
    W --> W3["③ 仅主<br/>(最终一致, 最低延迟)"]
```

### 4.4 数据怎么组织:小对象合并(WAL 思想)⭐⭐⭐

```mermaid
flowchart LR

    BAD --> B2["耗尽inode(数量固定)"]

    GOOD["✅ 合并成大文件 ⭐"] --> G1["追加到读写文件(WAL)"]
    GOOD --> G2["达阈值(几GB)→转只读"]
    GOOD --> G3["新建读写文件接新对象"]

    style BAD fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style B1 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style B2 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style B3 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style GOOD fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style G1 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style G2 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style G3 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style PAR fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style P1 fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
```

> 💡 **小对象合并是核心优化**(本质是 WAL):
> - 每个对象**追加**到当前**读写文件**;
> - 文件达阈值(几 GB)→ 转**只读**,新建读写文件;
> - 只读文件只服务读。
> - **并行瓶颈**:读写文件写必须串行 → 多核竞争 → **每核独占一个读写文件**。
>
> 这就是 Facebook **Haystack** 论文的核心思想(本章设计原型)。

### 4.5 对象查找(object_mapping)⭐⭐

合并后,怎么按 UUID 找对象?需要三要素:**哪个文件 + 起始偏移 + 大小**。

```mermaid
    OPT --> RD["关系库<br/>(B+树, 读快写慢)"]
    CHOOSE["选关系库 ⭐<br/>(write-once-read-many)"]
    DEPLOY["每数据节点 SQLite<br/>(映射数据节点内隔离)"]

    style LOOK fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style NEED fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style OPT fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style RK fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style RD fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style CHOOSE fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style DEPLOY fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
```

| object_mapping 字段 | 含义 |
|---------------------|------|
| object_id | 对象 UUID |
| file_name | 含该对象的文件名 |
| start_offset | 文件内起始地址 |
| object_size | 字节数 |

> 📝 **选型逻辑**:数据访问是 **write-once-read-many**(LinkedIn:95% 读)→ **读性能优先** → 关系库(B+树)优于 RocksDB(SSTable)。映射数据**节点内隔离**(无需跨节点共享)→ **每节点部署 SQLite**(文件型,轻量)。

> 💡 **注意**:这里选关系库是因为**对象映射表是读多写少**;但**元数据存储**(下一节)在海量规模下用 RocksDB/embedded 更常见(2026 增量会讲)。两个不同场景,别混淆。

## 5. 持久性(Durability)⭐⭐⭐⭐⭐(本章难点)

> 📝 **耐久性是对象存储的灵魂**——S3 11 个 9 意味着存 1000 万对象,1000 万年才丢 1 个。

### 5.1 失败域隔离(Failure Domain)

```mermaid
    style R3 fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style N1 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style AZ fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
```

### 5.2 3 副本复制 vs 纠删码 ⭐⭐⭐⭐⭐(核心抉择)

```mermaid
flowchart LR
    DUR["提升耐久"] --> REP["① 3副本复制"]
    DUR --> EC["② 纠删码 ⭐"]
    REP --> REPC["3份完整副本<br/>6个9耐久<br/>200%存储开销"]
    EC --> ECC["分块+校验块<br/>11个9耐久<br/>50%存储开销"]

    style DUR fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style REP fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style EC fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style REPC fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style ECC fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
```

**3 副本**:3 个完整副本。盘年故障率 0.81% → 可靠性 `1-(0.0081)³ ≈ 6 个 9`。

**纠删码**(Erasure Coding, Reed-Solomon):把数据**分块** + 算**校验块**,散布到不同失败域。例 **(8+4)**:8 数据块 + 4 校验块,12 块散到 12 个失败域,**最多 4 节点宕机仍能重建**。

```mermaid
flowchart LR
    EC["(8+4) 纠删码"] --> D1["d1 数据块"]
    EC --> D2["d2"]
    EC --> D3["d3"]
    EC --> D4["d4...d8"]
    EC --> P1["p1 校验块"]
    EC --> P2["p2...p4"]
    D3 -.->|"d3/d4丢失"| REC["用剩余数据块+校验块<br/>解方程重建丢失块"]

    style EC fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style D1 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style D2 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style D3 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style D4 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style P1 fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style P2 fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style REC fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
```

**对比表**(必背):

| 维度 | 3 副本 | 纠删码 | 胜者 |
|------|--------|--------|------|
| **耐久** | 6 个 9 | 11 个 9 | 纠删码 |
| **存储效率** | 200% 开销 | 50% 开销 | 纠删码 |
| **计算** | 无 | 算校验块耗 CPU | 副本 |
| **写性能** | 复制即可 | 写前算校验,延迟高 | 副本 |
| **读性能** | 单副本读 | 读多块重组;故障更慢 | 副本 |

> 💡 **选型经验**:**延迟敏感用副本;降本用纠删码**。原书主用副本(说纠删码复杂),但 **2026 真实 S3 主力是纠删码**(成本 + 11 个 9 碾压)——见 2026 增量。

### 5.3 数据校验(Checksum)

> 📝 **静默数据损坏**(bit rot)在大规模是常态——内存/磁盘 bit 翻转,盘没坏但数据错了。

```mermaid
flowchart LR
    WRITE["写入对象"] --> APP["末尾追加对象checksum"]
    SEAL["文件转只读"] --> WHOLE["末尾加整文件checksum"]
    READ["读取"] --> V["算checksum比对"]
    V -->|不匹配| REC2["从其他失败域读+重建"]
    V -->|匹配| OK["数据无损"]

    style WRITE fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style APP fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style SEAL fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style WHOLE fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style READ fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style V fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style REC2 fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style OK fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
```

- **设计**:每个对象末尾加 checksum;文件转只读前加整文件 checksum(MD5/SHA1/HMAC)。
- **读取**:取数据 + checksum,重算比对 → 不匹配则从其他失败域读 + 重建。

### 7.2 Multipart Upload(大文件分段)

```mermaid
sequenceDiagram
    participant C as 客户端
    participant DS as 数据存储
    C->>DS: 发起 multipart 上传
    DS-->>C: 返回 uploadID
    Note over C: 切片(如1.6GB→8×200MB)
    C->>DS: 上传 part1(+uploadID)
    DS-->>C: ETag(md5 of part)
    C->>DS: 上传 partN...
    C->>DS: complete(uploadID, part号, ETags)
    DS->>DS: 按 part号重组
    DS-->>C: 成功
```

**为什么 multipart**:大文件直传慢 + 网络中断要重传全部。**切片独立上传** + 断点续传 + 并行。每个 part 返回 **ETag(md5 校验)**;complete 后按 part 号重组。**残留 part 由 GC 回收**。

### 示例 2:object_mapping 表(SQLite)

```sql
-- 每数据节点本地 SQLite(映射数据节点内隔离)
CREATE TABLE object_mapping (
    object_id    TEXT PRIMARY KEY,   -- UUID
    file_name    TEXT,               -- 合并后的大文件
    start_offset INTEGER,            -- 文件内起始偏移
    object_size  INTEGER             -- 字节数
);
-- 读多写少(write-once-read-many)→ B+树关系库优于 RocksDB
SELECT file_name, start_offset, object_size
FROM object_mapping WHERE object_id = ?;
```

### 示例 3:版本化元数据(CQL / TIMEUUID)

```sql
-- 版本化: 不覆盖, 插新行(同name不同version)
CREATE TABLE object (
    bucket_id      uuid,
    object_name    text,
    object_id      uuid,             -- 每版本不同UUID
    object_version timeuuid,         -- TIMEUUID, 当前版=最大
    is_deleted     boolean,          -- delete marker
    PRIMARY KEY ((bucket_id, object_name), object_version)
);
-- 查当前版本: 聚类键 object_version 降序取第一条
SELECT * FROM object
WHERE bucket_id=? AND object_name=?
ORDER BY object_version DESC LIMIT 1;
```

### 示例 4:multipart 上传(伪码)

```python
def multipart_upload(file_path, bucket, key, part_size=200*1024*1024):
    upload_id = s3.initiate_multipart(bucket, key)      # 发起
    parts = []
    for part_no, chunk in enumerate(split(file_path, part_size), 1):
        etag = s3.upload_part(bucket, key, upload_id, part_no, chunk)  # ETag=md5
        parts.append((part_no, etag))
    s3.complete_multipart(bucket, key, upload_id, parts)  # 重组; 残留part由GC回收
```

## 🪤 追问陷阱(面试官最爱问,本章集)

1. **"块/文件/对象存储区别?"** → 块(原始块,VM/DB);文件(目录树,NFS/SMB);**对象(不可变,REST,海量冷数据)**。
2. **"对象存储为什么慢?"** → **刻意取舍**:牺牲性能换极高耐久 + 海量 + 低成本(面向冷数据)。
3. **"元数据和数据为什么要分离?"** → **类 UNIX inode 思想**:元数据可变、数据不可变,分离后**各自独立优化**。
4. **"小对象怎么存?"** → **合并成大文件(WAL 思想)**:追加到读写文件,达阈值转只读;每核独占读写文件避串行。
5. **"怎么按 UUID 找合并文件里的对象?"** → object_mapping 表(object_id→file_name+start_offset+object_size);读多写少选**关系库(SQLite)**。
6. **"怎么保证 6 个 9 耐久?"** → **3 副本**(0.81% 故障率 → 1-0.0081³≈6 个 9)+ **失败域隔离**(跨机架/AZ)+ checksum。
7. **"3 副本 vs 纠删码?"** → 副本:200% 开销/6 个 9/写读快;**纠删码:50% 开销/11 个 9/写前算校验慢**。2026 真实 S3 主用纠删码。
8. **"数据损坏(盘没坏但数据错)怎么办?"** → **静默损坏是常态**,用 checksum 比对,不匹配从其他失败域读 + 重建。
9. **"object 表怎么分片?"** → **hash(bucket_name, object_name)**:均匀 + 支持 name 查询。bucket_id 会热点,object_id 不支持 name 查询。
10. **"分片下列桶为什么难?"** → 各分片返回数不一,**分页 offset 每分片不同**。解法:**反规范化单独 list 表**(按 bucket_id 分片)。
11. **"版本化怎么实现?"** → 不覆盖,插新行(object_version=TIMEUUID),当前版=最大 TIMEUUID;删除=插 delete marker。
12. **"大文件怎么上传?"** → **multipart 分段**:切片独立上传(断点续传),每 part 返 ETag,complete 后重组;残留 part 由 GC 回收。
13. **"GC 怎么做?"** → 不立即删,定期 **compaction**:复制存活对象到新文件(跳过删除标记),更新 mapping 用事务。
14. **"写入确认时机怎么选?"** → 全 3 副本(强一致高延迟)/ 主+1(中)/ 仅主(最终一致低)。对象冷数据常选低延迟。
15. **"2026 S3 默认一致模型?"** → **强一致(read-after-write,2020.12 起)**。
16. **"本题工业原型?"** → Facebook **Haystack**(小对象合并+元数据分离)+ **f4**(温数据纠删码)。
17. **"怎么降本?"** → 纠删码(50% vs 200%)+ **分级存储**(热 Standard/冷 Glacier)+ CAS 去重 + 小对象合并。

**核心 Takeaways**:

1. **对象存储是"刻意取舍"**——牺牲性能换极高耐久(6-11 个 9)+ 海量 + 低成本,面向冷数据;不可变、REST 访问、扁平结构。
2. **元数据/数据分离**(类 UNIX inode)是核心思想:元数据可变、数据不可变,各自独立优化。
3. **小对象合并成大文件**(WAL/Haystack 思想):追加到读写文件,达阈值转只读;**每核独占读写文件**避串行;object_mapping 用 SQLite(读多写少)。
4. **持久性靠副本/纠删码 + 失败域 + checksum**:3 副本 6 个 9(200% 开销);**纠删码 11 个 9(50% 开销)**;副本跨机架/AZ;checksum 防静默损坏。
5. **2026 真实 S3 主用纠删码**(成本+耐久碾压副本),CLAY 码降修复带宽;冷热分层(副本热/EC 冷)。
6. **元数据分片**:hash(bucket_name, object_name);**分片下列桶难**(每分片 offset 不同)→ 反规范化单独 list 表。
7. **版本化**用 TIMEUUID(不覆盖 + delete marker);**multipart** 分段上传大文件;**GC** compaction 回收(事务更新 mapping)。
8. **2020.12 起 S3 默认强一致**(read-after-write);checksum 多算法(CRC32C 硬件加速,MD5 不安全)。
9. **分级存储降本**(Standard/IA/Glacier/Deep Archive/Intelligent-Tiering);CAS 去重省 PB。
10. **工业原型是 Facebook Haystack**(2010,小对象合并)/ **f4**(温数据 EC)/ **Tectonic**(2021 统一);**MinIO** 是自建开源首选。
