# Volume 2 · Chapter 13: 设计证券交易系统 (Design a Stock Exchange)

> **本章定位**:证券交易是**"极致低延迟 + 确定性撮合 + 强一致可重放"**的硬核系统设计压轴题——它是 NYSE/NASDAQ/CME/LMAX/Binance 的设计骨架。它把 V2-Ch12 数字钱包的强一致(资金预扣)、Vol.1 的消息队列、V2-Ch7 的有状态服务全用上,并把延迟从毫秒级压到**微秒甚至纳秒级**。灵魂是七件事:**① 订单簿(order book,价位链表 O(1))② 撮合引擎(matching engine,价格-时间优先 FIFO)③ 定序器(sequencer,确定性单写)④ 单服务器低延迟设计(全在内存,mmap 消息总线,CPU 钉核,无锁环形队列)⑤ 事件溯源(event sourcing,可重放重建状态)⑥ 热备 + Raft 跨机房高可用 ⑦ 市场数据 UDP 多播(multicast,公平同时送达)**。它最大的考点是**把延迟压到极限,同时保证强一致和可重放**——一道题考透撮合引擎 + 低延迟工程 + 分布式一致性。

> **本章和原书的区别**:原书把**订单簿数据结构(价位链表 + Map)、撮合 FIFO、sequencer 单写确定性、单服务器 mmap 消息总线、CPU 钉核 application loop、event sourcing、hot-warm + Raft、ring buffer、reliable UDP multicast、colocation**讲得相当完整,是面试标准答案。但**原书刻意回避了真实低延迟栈的硬核细节**——LMAX Disruptor(无锁环形队列,撮合引擎的灵魂模式)只在参考链接里提一句;**FPGA 硬件加速撮合**(NYSE/NASDAQ/TMX 实际用)完全没讲;**kernel bypass / DPDK / Solarflare**(内核旁路降延迟)没讲;**SBE(Simple Binary Encoding)**只在图里出现"FIX over SBE"没解释;**PTP(IEEE 1588 纳秒级时钟同步)**没讲;**订单簿实际用红黑树/跳表**(价位链表查价位 O(1) 但查"最优买卖"和"遍历价位"不行)没讲透;**Reg NMS / MiFID II / Best Execution 监管**没讲;**加密货币撮合(Binance/FTX 式,云端 + 内存撮合,与监管交易所差异)**只在收尾一段。本章把这些全补上——**低延迟是核心,2026 增量尤其重要**。

**功能**:① 客户端下限价单/撤单;② 实时收到匹配成交;③ 实时查看订单簿;④ 历史数据/蜡烛图。
**规模**:至少数万用户同时交易、至少 100 标的、**每天数十亿订单**。
**监管**:交易所是受监管设施,**必须做风控**(如某用户一天最多交易 100 万股 AAPL)。
**钱包**:用户下单时**预扣资金**(订单在簿等待成交期间资金冻结),防超支(接 V2-Ch12)。

**非功能性**(背):

```mermaid

    NF --> FT["容错+快速恢复"]

    NF --> SEC["安全: KYC + 防DDoS"]

    style NF fill:#FFE082,stroke:#F9A825,color:#1f1f1f

    style LAT fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style SEC fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
```

- **可用性 ≥99.99%**:交易所声誉受损,**停机几秒都伤**(每天停机上限 8.64 秒)。
- **容错 + 快速恢复**:限制生产事故影响。
- **延迟**:**往返 ms 级**,特别关注 **99 分位**(市价单进入交易所到成交返回)。**99 分位持续高 → 少数用户极差体验**。
- **安全**:KYC 开户验证身份;公共行情页防 DDoS。

**估算**(背):

```
100 标的, 10 亿订单/天
NYSE 周一至五 9:30-16:00 ET = 6.5 小时
QPS = 10亿 / 6.5 / 3600 ≈ 43,000
峰值 QPS = 5× = 215,000  (开盘/收盘交易量显著更高)
→ 高吞吐 + 低延迟 + 强一致,三难全占
```

> 💡 **核心洞察**:**交易所三难全占——高吞吐(43k QPS)+ 低延迟(µs-ms)+ 强一致可重放**。这逼出了"单服务器全内存 + mmap + CPU 钉核 + 无锁环形 + event sourcing"这套反直觉但极致的设计。

| 概念 | 说明 |
|------|------|
| **Broker(经纪商)** | 零售客户端通过 broker 交易(Schwab/Robinhood/Etrade/Fidelity)。提供友好 UI 下单+看行情 |
| **机构客户** | 大单+专用软件。**养老金**(少而大,需订单拆分降市场冲击);**对冲基金做市**(靠佣金返点,需**极低延迟**,不能看网页/App) |
| **限价单** | 固定价格的买卖单,**可能不立即成交或只部分成交** |
| **市价单** | 不指定价格,**按当前市价立即成交**,牺牲成本保成交(快速行情下有用) |
| **L1 行情** | **最优买价/卖价 + 量**(best bid/ask) |
| **L2 行情** | 比 L1 更多价位 |
| **L3 行情** | L2 + **每个价位排队的量**(撮合引擎内部用) |
| **蜡烛图** | 某时段 OHLC(开/收/高/低)+ 量。常见 1m/5m/1h/1d/1w/1M |
| **FIX 协议** | 1991,**金融信息交换** vendor-neutral 协议,tag=value 文本格式 |

**FIX 报文示例**(背,知道是 tag=value):

```
8=FIX.4.2 | 9=176 | 35=8 | 49=PHLX | 56=PERS |
52=20071123-05:30:00.000 | 11=ATOMNOCCC9990900 |
20=3 | 150=E | 39=E | 55=MSFT | 167=CS | 54=1 |
38=15 | 40=2 | 44=15 | 58=PHLX EQUITY TESTING |
59=0 | 47=C | 32=0 | 31=0 | 151=15 | 14=0 | 6=0 |
10=128 |
```

> 📝 **FIX 是 tag=value 文本协议**——可读但**慢**(解析+带宽)。2026 现代交易所用 **SBE(Simple Binary Encoding)** 二进制替代(后面 2026 增量讲)。


- 三个目的:**① 及时性公平(先来先服务)② 快速恢复重放 ③ 恰好一次**。
- **sequencer 还兼消息队列 + 事件存储**——类似两个 Kafka 流(一个进站订单,一个出站成交)。**Kafka 延迟如果更低更可预测,本来可以用 Kafka**——但低延迟交易所自己实现 sequencer(deep dive 讲)。

> 🪤 **追问陷阱(高频)**:"sequencer 为什么是单写?" → **多个 sequencer 会争抢 event store 写权,锁竞争浪费大量时间**。所以 sequencer 是**单写**(single writer),定序后再发 event store。**单写是确定性的基础**。

### 7.3 application loop + CPU 钉核 ⭐⭐⭐

```mermaid

    BEN["CPU 钉核好处"] --> B1["① 无上下文切换<br/>(CPU 全分给该 loop)"]
```

**撮合伪代码**(价格-时间优先,背逻辑):

```
match(newOrder, book):
    oppositeBook = (newOrder.side==BUY) ? book.sellBook : book.buyBook
    while newOrder.remainingQty > 0 and oppositeBook has price level that crosses:
        bestLevel = oppositeBook.bestPriceLevel   # 最优价位
        while bestLevel has orders and newOrder.remainingQty > 0:
            restingOrder = bestLevel.orders.head()  # 队头(先来的)
            fillQty = min(newOrder.remainingQty, restingOrder.remainingQty)
            emit Fill(newOrder, restingOrder, bestLevel.price, fillQty)  # 2笔成交
            newOrder.remainingQty -= fillQty
            restingOrder.remainingQty -= fillQty
            if restingOrder.remainingQty == 0:
                bestLevel.orders.removeHead()       # O(1) 双向链表
        if bestLevel empty: oppositeBook.removeLevel(bestLevel)
    if newOrder.remainingQty > 0:
        book.addRestingOrder(newOrder)              # 剩余进簿等待
```

### 13.1 LMAX Disruptor:无锁环形队列(撮合引擎灵魂)⭐⭐⭐⭐⭐

原书只在参考链接提一句 LMAX,但 **Disruptor 是现代低延迟撮合的事实模式**。


> 💡 **LMAX Disruptor 是原书 mmap 消息总线 + ring buffer 的工业实现**。**关键技巧**:
> - **无锁**:生产者用 **CAS(Compare-And-Swap)** 抢下一个序列号,无锁无等待。
> - **无 GC**:预分配定长数组,事件对象复用 → **零垃圾** → 避 JVM GC 抖动。
> - **缓存行填充(padding)**:序列号前后填充 7 个 long,让序列号独占 64B 缓存行 → 避 **false sharing**(多核缓存一致性导致的隐形性能杀手)。
> - **单线程消费者**:每个消费者单线程跟序列号,无锁。
>
> 🔄 **2026 话术**:"原书的 mmap 消息总线和 ring buffer,工业上就是 **LMAX Disruptor**——无锁环形队列,CAS 抢序列号,预分配无 GC,缓存行填充避 false sharing。**单线程 1000万+ msg/s,延迟 <1µs**。这是现代低延迟撮合的事实模式,LMAX 自己就是用 Disruptor 做零售外汇撮合。"

### 示例 1:订单簿 O(1) 三操作(Java,原书结构 + 双向链表优化)

```java
class PriceLevel {
    long limitPrice;            // 限价(用 long 表示价格,避浮点)
    long totalVolume;           // 该价位总量
    Order head;                 // 双向链表头(最早来的,先成交)
    Order tail;                 // 双向链表尾(新单加这)
}

class OrderBook {
    TreeMap<Long, PriceLevel> bids = new TreeMap<>(Collections.reverseOrder()); // 买:降序
    TreeMap<Long, PriceLevel> asks = new TreeMap<>();                          // 卖:升序
    Map<Long, Order> orderMap = new HashMap<>();   // orderID → Order, 撤单O(1)定位

    // ① 下新单:加到价位链表尾 O(1)(价位不存在则建)
    void place(Order o) {
        PriceLevel pl = getOrCreateLevel(o.side, o.price);
        if (pl.tail == null) { pl.head = pl.tail = o; }
        else { pl.tail.next = o; o.prev = pl.tail; pl.tail = o; }
        pl.totalVolume += o.qty;
        orderMap.put(o.id, o);
    }

    // ② 匹配成交:从价位链表头删 O(1)
    void match(Order newOrder) {
        TreeMap<Long, PriceLevel> opp = newOrder.isBuy() ? asks : bids;
        while (newOrder.remaining > 0 && !opp.isEmpty()) {
            Map.Entry<Long, PriceLevel> best = opp.firstEntry();  // 最优价位
            PriceLevel pl = best.getValue();
            while (pl.head != null && newOrder.remaining > 0) {
                Order resting = pl.head;
                long fillQty = Math.min(newOrder.remaining, resting.remaining);
                emitFill(newOrder, resting, pl.limitPrice, fillQty);  // 2笔成交
                newOrder.remaining -= fillQty;
                resting.remaining  -= fillQty;
                pl.totalVolume     -= fillQty;
                if (resting.remaining == 0) {
                    pl.head = resting.next;            // 链表头删 O(1)
                    if (pl.head != null) pl.head.prev = null;
                    if (pl.tail == resting) pl.tail = null;
                    orderMap.remove(resting.id);
                }
            }
            if (pl.head == null) opp.remove(best.getKey());  // 价位空了删掉
        }
        if (newOrder.remaining > 0) place(newOrder);   // 剩余进簿等待
    }

    // ③ 撤单:Map 定位 + 链表删 O(1)
    boolean cancel(long orderId) {
        Order o = orderMap.get(orderId);
        if (o == null) return false;
        if (o.prev != null) o.prev.next = o.next; else o.level.head = o.next;
        if (o.next != null) o.next.prev = o.prev; else o.level.tail = o.prev;
        o.level.totalVolume -= o.remaining;
        orderMap.remove(orderId);
        return true;
    }
}
```

> 💡 **TreeMap(红黑树)**按价位排序,`firstEntry()` 查最优 O(log n);同价位用双向链表 FIFO;`orderMap` 撤单 O(1) 定位。**这就是三件套组合**。

```python
class Sequencer:
    """单写定序器: 从各组件 ring buffer 拉事件, 盖连续序列号, 发 event store"""
    def __init__(self):
        self.seq = 0                          # 单调递增连续序列号

    def stamp(self, event):
        self.seq += 1
        event.sequence = self.seq             # 盖序列号
        self.event_store.append(event)        # 发 event store(单写, 无锁竞争)
        return event

    def detect_gap(self, seen_seq):
        # 序列号必须连续, 缺号=丢消息→触发恢复

            trigger_recovery(from_seq=seen_seq)
```

### 示例 3:event sourcing 状态重建

```python
class OrderStateStore:
    """event sourcing: 不存当前态, 重放事件恢复状态"""
    def __init__(self):
        self.orders = {}                      # orderID → 当前态(由事件投影出来)

    def apply(self, event):
        if event.type == 'NewOrderEvent':
            self.orders[event.order_id] = {
                'status': 'new', 'filled': 0, 'remaining': event.qty, ...}
        elif event.type == 'OrderFilledEvent':
            o = self.orders[event.order_id]
            o['filled']    += event.fill_qty
            o['remaining'] -= event.fill_qty
            o['status'] = 'filled' if o['remaining'] == 0 else 'partially_filled'
        elif event.type == 'CancelEvent':
            self.orders[event.order_id]['status'] = 'canceled'

    def rebuild(self, event_log):
        """主挂后:从 event store 重放全部事件→恢复状态(确定性)"""
        for event in sorted(event_log, key=lambda e: e.sequence):
            self.apply(event)                 # 同序重放→同结果(功能确定性)
```

### 示例 4:LMAX Disruptor 风格无锁环形队列(简化)

```python
# Disruptor 核心: 预分配数组 + CAS 抢序列号 + 缓存行填充
import threading
class RingBuffer:
    def __init__(self, size=1024*16):
        self.size = size
        self.buffer = [None] * size           # 预分配, 无对象创建→无GC
        self.cursor = 0                       # 消费者已处理到的序列号
        self.next_seq = 1                     # 生产者下一个要写的序列号(CAS保护)
        self._pad1 = self._pad2 = [0]*7       # 缓存行填充(避false sharing, 实际用@cached)

    def publish(self, event):                 # 生产者:CAS 抢序列号(无锁)
        seq = self.next_seq
        self.next_seq += 1                    # 原子操作(实战用CAS)
        self.buffer[seq % self.size] = event  # 环形定位
        # 消费者各自跟序列号, 单线程消费→无锁

    def consume(self, seq):                   # 消费者单线程
        return self.buffer[seq % self.size]
```

### 示例 5:撮合伪代码(价格-时间优先,完整)

```python
def match(new_order, book):
    """FIFO 价格-时间优先撮合"""
    opp = book.asks if new_order.is_buy() else book.bids
    while new_order.remaining > 0 and opp.has_crossing_level(new_order):
        best_level = opp.best_level()         # 最优价位(红黑树firstEntry)
        while best_level.head and new_order.remaining > 0:
            resting = best_level.head         # 队头(先来的先成交)
            fill = min(new_order.remaining, resting.remaining)
            emit_fill(new_order, resting, best_level.price, fill)  # 2笔成交(买/卖)
            new_order.remaining  -= fill
            resting.remaining    -= fill
            best_level.volume    -= fill
            if resting.remaining == 0:
                best_level.remove_head()      # O(1) 双向链表
        if best_level.head is None:
            opp.remove_level(best_level)      # 价位空了删
    if new_order.remaining > 0:
        book.add_resting(new_order)           # 剩余进簿等待
```

## 🪤 追问陷阱(面试官最爱问,本章集)

1. **"撮合引擎怎么保证确定性?"** → **sequencer 单写定序**(盖连续序列号)+ **event sourcing**(不可变事件日志可重放)→ 同序重放产生同结果。**确定性是高可用基础**。
2. **"订单簿数据结构怎么设计?"** → **价位双向链表(同价位 FIFO)+ Map<orderID> 快速定位 + 红黑树/跳表做价位索引**。下单=链表尾插 O(1);匹配=链表头删 O(1);撤单=Map 定位+链表删 O(1);查最优=红黑树 O(log n)。
3. **"为什么原书的 List 不行?"** → 普通 list 撤单(删中间)不是 O(1)。改**双向链表**后增/匹配/撤全 O(1)。
4. **"撮合算法是什么?"** → **FIFO 价格-时间优先**(同价位先来的先成交)。期货还有 FIFO+LMM(做市商预留比例)。
5. **"为什么全放单服务器?"** → 网络往返 ~500µs 多跳累加 ms;磁盘顺序写仍数十 ms。**单服务器 + mmap(/dev/shm) 消除网络磁盘,通信 <1µs**。
6. **"mmap 消息总线怎么工作?"** → mmap 把文件映射进进程内存;backing 文件在 /dev/shm(内存文件系统)→ 访问**完全不触发磁盘**。组件间通信亚微秒。
7. **"application loop 为什么单线程钉 CPU?"** → **无上下文切换 + 无锁竞争 → 低 99 分位延迟**。代价是编码复杂(每任务精算时间)。
8. **"sequencer 为什么是单写?"** → 多 sequencer 抢 event store 写权 = 锁竞争浪费时间。**单写 sequencer 盖号再发 event store,超快**。
9. **"event sourcing 和传统存状态有何不同?"** → 传统存当前态(出错难追溯);**event sourcing 存不可变事件日志(唯一真相源),重放恢复状态**。适配交易所(订单状态极复杂 + 确定性重放)。
10. **"热备怎么做?"** → **hot 主**正常撮合+发 event store;**warm 备**收同样事件静默处理不发。主挂 warm 立即接管;备挂重启从 event store 重放恢复。**跨机用 reliable UDP(Aeron)复制 event store**。
11. **"Raft 怎么选主?"** → leader 发心跳 AppendEntries;follower 超时未收→触发选举→RequestVote→多数票(N/2+1)成新 leader。**term 低者不能当 leader;split vote 重来**。
12. **"RTO 和 RPO 对交易所是什么?"** → **RTO 秒级**(需自动 failover+降级);**RPO≈0**(数据丢失不可接受,Raft 多副本共识保证)。
13. **"行情怎么公平送达?"** → 比别人延迟低=看未来的神谕。**reliable UDP 多播**(同组理论同时收)+ 订阅随机化。UDP 不可靠→NORM 重传。
14. **"colocation 是什么?"** → broker 租交易所机房服务器,下单延迟≈光缆长度。**不破坏公平**(付费 VIP)。CME/NYSE 提供 colo 服务。
15. **"99 分位延迟为什么重要?"** → 99 分位持续高 = 少数用户极差体验。**HdrHistogram 测量**。**抖动元凶:JVM safepoint(STW GC/代码反优化)** → 治理 GC 是关键。
16. **"FIX 协议是什么?"** → 1991 金融信息交换协议,**tag=value 文本**。可读但慢。**2026 用 SBE 二进制替代**(零拷贝,紧凑,<1µs 编解码)。
17. **"2026 极致延迟怎么搞?"** → **FPGA 硬件加速撮合(tick-to-trade <100ns)** + **LMAX Disruptor 无锁环形(<1µs)** + **Kernel Bypass(DPDK/Solarflare,亚µs 网络)** + **SBE 编码** + **PTP 纳秒时钟**。
18. **"加密交易所和传统差异?"** → 加密**云端+内存撮合**,7×24,监管宽松,撮合清算一体,trading pair 数千,延迟宽松(ms)。DeFi DEX 用 **AMM(x*y=k)无订单簿**。
19. **"NBBO 是什么?"** → **Reg NMS 的全国最优买卖**(National Best Bid Offer)——订单保护规则,经纪商必须拿最优价(Best Execution),禁止跨市场穿价。
20. **"LMAX Disruptor 为什么快?"** → **无锁(CAS 抢序列号)+ 无 GC(预分配)+ 缓存行填充(避 false sharing)+ 单线程消费**。单线程 1000万+ msg/s,<1µs 延迟。
21. **"为什么不能用 Kafka 做 sequencer?"** → Kafka 延迟不够低且不够可预测(磁盘+网络+副本)。**低延迟交易所自研 sequencer + mmap event store**。没严格延迟要求本来可以用 Kafka。
22. **"关键路径为什么连 logging 都去掉?"** → 延迟=∑关键路径执行时间。logging 涉及磁盘 IO → 增延迟。**关键路径只留必要组件**,行情和上报走非关键路径。

**核心 Takeaways**:

1. **交易所三难全占**——高吞吐(43k QPS)+ 低延迟(µs-ms)+ 强一致可重放。这逼出"单服务器全内存 + mmap + CPU 钉核 + 无锁环形 + event sourcing"的极致设计。
2. **三流分离**——**交易流是关键路径**(延迟敏感,连 logging 都去掉);行情流和上报流非关键(延迟宽松)。
3. **撮合引擎的灵魂是确定性**——给定订单序列重放产生相同成交。**sequencer 单写定序 + event sourcing** 保证。
4. **订单簿数据结构 = 价位双向链表(同价位 FIFO)+ Map<orderID> 快速定位 + 红黑树/跳表价位索引**。下单/匹配/撤全 O(1),查最优 O(log n)。
5. **撮合算法 = FIFO 价格-时间优先**(同价位先来先成交)。
6. **低延迟单服务器四件套**:全组件同机(消网络)+ mmap /dev/shm(消磁盘,<1µs)+ application loop 单线程(消锁)+ CPU 钉核(消上下文切换)。从数十 ms 降到数十 µs。
7. **event sourcing**:不存当前态存不可变事件日志,重放恢复状态。适配订单状态极复杂 + 确定性重放。
8. **高可用 = hot-warm + Raft 跨机房**。主挂 warm 立即接管;备挂从 event store 重放恢复;跨机用 reliable UDP(Aeron)复制。**RTO 秒级,RPO≈0**。
