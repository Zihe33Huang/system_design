# Volume 2 · Chapter 8: 设计分布式邮件服务 (Design a Distributed Email Service)

> **本章定位**:分布式邮件是**"存储极重 + 异步可靠投递 + 送达率 + 全文搜索"**的综合业务题——它是 Gmail/Outlook/QQ 邮箱的设计骨架。它把 Vol.1 Ch1 的缓存/MQ、V2-Ch4 的消息队列、Ch7 的有状态服务全用上。灵魂是六件事:**① 收发协议(SMTP/IMAP/POP)② 元数据怎么存(自定义分布式DB + 反规范化)③ 附件怎么存(S3 对象存储)④ 怎么实时推送新邮件(WebSocket)⑤ 怎么全文搜索(Elasticsearch / LSM 原生)⑥ 送达率(为什么 50% 邮件是垃圾 + SPF/DKIM/DMARC)**。它是少有的"协议古老(1970s SMTP)但规模现代(10亿用户/PB级)"的题。

> **本章和原书的区别**:原书把**分布式邮件的架构和元数据建模讲得相当完整**——传统 Maildir 演进、收发流程、反规范化解决 NoSQL 读/未读查询、JWZ 会话线程、送达率(SPF/DKIM/DMARC)、Elasticsearch vs 原生搜索都覆盖,是面试标准答案。但**用 HTTP/REST 作客户端协议**,而 2026 现代邮件客户端协议是 **JMAP**(HTTP/JSON 替代 IMAP,RFC 8621,快得多);**Gmail 用"自定义 DB"一笔带过**——实际是 **Bigtable + Colossus(GFS)+ 原生搜索**,这是 Google 的真实栈;**反垃圾只说"过滤",没讲 ML**(Gmail 用 TensorFlow);**认证只提 SPF/DKIM/DMARC,没提 BIMI(品牌标识)/ARC(转发链)**;**附件去重**只在收尾提一句——实际群发场景去重是省 PB 级存储的关键;**冷存储分层**没讲(Gmail 老邮件上冷存)。本章补上。

**非功能性**:**可靠(不能丢邮件)**;可用(多副本+部分故障可运行);可扩展;灵活可扩展(传统协议功能有限,可能要自定义协议)。

**估算**(背,存储很震撼):

```
10亿用户
发: 人均10封/天 → 发送 QPS = 10亿×10/10^5 = 100,000
收: 人均40封/天, 元数据50KB
  元数据/年 = 10亿 × 40 × 365 × 50KB = 730 PB ⚠️
附件: 20%含附件, 均500KB
  附件/年 = 10亿 × 40 × 365 × 20% × 500KB = 1,460 PB ⚠️
→ 必须分布式DB + 冷热分层 + 去重
```

> 💡 **核心洞察**:**邮件是存储极重型**(每年 PB 级)。架构核心是**存储优化**:分布式元数据DB + 附件对象存储 + 去重 + 冷热分层。

## 2. 邮件协议 101 ⭐⭐⭐⭐⭐

```mermaid
flowchart LR
    PROTO["邮件协议"] --> SMTP["SMTP<br/>(服务器间发送)"]
    PROTO --> POP["POP<br/>(下载后删, 单设备)"]
    PROTO --> IMAP["IMAP ⭐<br/>(读在服务器, 多设备)"]
    PROTO --> HTTP["HTTP/ActiveSync<br/>(webmail/移动)"]

    style PROTO fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style SMTP fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style POP fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style IMAP fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style HTTP fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
```

| 协议 | 用途 | 特点 |
|------|------|------|
| **SMTP** | **服务器之间发送** | 标准发送协议 |
| **POP** | 下载到本地 | **下载后从服务器删除** → 只能一个设备访问;要下整封(大附件慢) |
| **IMAP** ⭐ | 读取(主流) | **邮件留服务器**,多设备访问;点击才下载;慢连接友好(先下头) |
| **HTTP/ActiveSync** | webmail/移动 | Outlook 用 ActiveSync over HTTPS |

**其它基础**:
- **DNS MX 记录**:定位收件域的邮件服务器(带优先级,低的优先)。`gmail.com` 的 MX 优先级 5 → 优先用 `gmail-smtp-in.l.google.com`。
- **附件**:**Base64 编码**(二进制→文本传输);大小限制(Outlook 20MB / Gmail 25MB);**MIME** 规范。

> 📝 **传统邮件服务器**:单机 + **Maildir**(每封邮件一个文件,用户目录)。**不扩展**(数十亿邮件磁盘 IO 瓶颈)+ **无高可用**(盘坏/机挂丢数据)→ 需分布式。

## 3. 分布式邮件架构 ⭐⭐⭐⭐⭐

### 3.1 核心组件

```mermaid
flowchart TB
    U["Webmail 用户"] --> WS["Web 服务器<br/>(无状态, REST API)"]
    U --> RT["实时服务器 ⭐<br/>(有状态, WebSocket<br/>推送新邮件)"]
    WS --> META[("元数据 DB<br/>自定义分布式DB")]
    WS --> CACHE[("分布式缓存<br/>Redis, 近期邮件")]
    WS --> ATT[("附件存储<br/>S3 对象存储")]
    WS --> SEARCH[("搜索<br/>Elasticsearch/原生")]
    SMTPIN["SMTP 接收"] --> Q["入站队列<br/>(解耦)"] --> WORK["邮件处理worker<br/>(反垃圾/病毒)"]
    WORK --> META
    WORK --> ATT
    WORK --> RT

    style U fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style WS fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style RT fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style META fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style CACHE fill:#90CAF9,stroke:#1976D2,color:#1f1f1f
    style ATT fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style SEARCH fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style SMTPIN fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style Q fill:#90CAF9,stroke:#1976D2,color:#1f1f1f
    style WORK fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
```

| 组件 | 职责 |
|------|------|
| **Web 服务器** | 无状态,处理 REST API(登录/收发/读文件夹) |
| **实时服务器** ⭐ | **有状态**,WebSocket 推送新邮件(Vol.1 Ch12 同源) |
| **元数据 DB** | 邮件元数据(主题/正文/发收件人) |
| **附件存储** | S3(大文件,Cassandra 不适合:blob 实际 <1MB + 占行缓存) |
| **分布式缓存** | Redis 缓存近期邮件(82% 读在 16 天内) |
| **搜索存储** | 倒排索引全文搜索 |

### 3.2 发送流程 ⭐⭐

```mermaid
sequenceDiagram
    participant U as 用户
    participant LB as LB
    participant WS as Web服务器
    participant Q as 出站队列
    participant W as SMTP发送worker
    participant R as 收件方服务器
    U->>LB: 发邮件
    LB->>WS: 限流后路由
    WS->>WS: 校验(大小/同域快捷)
    alt 同域(收发同邮件服务)
        WS->>WS: 直接入收件人存储(不走出站)
    else 跨域
        WS->>Q: 入出站队列(失败入错误队列)
        Q->>W: worker拉取
        W->>W: 反垃圾/病毒检查
        W->>W: 存"已发送"文件夹
        W->>R: SMTP发给收件方
        Note over W,R: 失败→指数退避重试
    end
```

**发送流程**(背):
1. 用户发邮件 → LB 限流 → Web 服务器。
2. **基本校验**(大小限制等)。
3. **同域快捷**:收发同域 → 直接入存储,收件人 REST 拉取,**不走出站队列**。
4. **跨域**:入**出站队列**(失败入错误队列)→ SMTP 发送 worker 拉取(反垃圾/病毒检查)→ 存"已发送"→ SMTP 发给收件方。
5. 失败 → **指数退避重试**;监控队列堆积。

### 3.3 接收流程 ⭐⭐

```mermaid
sequenceDiagram
    participant S as 发件方服务器
    participant LB as SMTP LB
    participant SS as SMTP服务器
    participant Q as 入站队列
    participant W as 邮件处理worker
    participant RT as 实时服务器
    participant U as 收件用户
    S->>LB: SMTP投递
    LB->>SS: 分发(无效地址拒绝)
    SS->>SS: 大附件→S3
    SS->>Q: 入入站队列(缓冲)
    Q->>W: worker拉取
    W->>W: 反垃圾/病毒过滤
    W->>W: 存存储+缓存+对象存储
    alt 收件人在线
        W->>RT: 推送
        RT->>U: WebSocket实时推送新邮件
    else 离线
        Note over U: 上线后REST拉取
    end
```

**接收流程**(背):
1. SMTP 投递 → SMTP LB → SMTP 服务器(无效地址直接拒,避免无谓处理)。
2. 大附件 → 附件存储(S3)。
3. 入**入站队列**(缓冲,削峰)。
4. 邮件处理 worker:**反垃圾/病毒过滤** → 存储层 + 缓存 + 对象存储。
5. 收件人在线 → 实时服务器 **WebSocket 推送**;离线 → 上线后 REST 拉。

> 💡 **队列是关键**:出站/入站队列**解耦 SMTP worker 与 web/SMTP 服务器**,各自独立扩缩;队列还做**削峰缓冲**(邮件量突增)。

### 4.4 反规范化:读/未读查询 ⭐⭐⭐(NoSQL 经典)

> 📝 **痛点**:**NoSQL 一般只支持分区键/聚类键查询**。`is_read` 既非分区键也非聚类键,`WHERE is_read=false` 查询会被拒。

```mermaid
flowchart LR
    Q["查未读邮件"] --> BAD["❌ NoSQL拒<br/>WHERE is_read=false<br/>(is_read非键)"]
    Q --> DENORM["✅ 反规范化<br/>拆两张表"]
    DENORM --> T1["read_emails 表<br/>(已读)"]
    DENORM --> T2["unread_emails 表<br/>(未读)"]
    NOTE["标已读: 从unread删→插read<br/>用空间换查询性能"]

    style Q fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style BAD fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style DENORM fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style T1 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style T2 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style NOTE fill:#90CAF9,stroke:#1976D2,color:#1f1f1f
```

**反规范化**(背):拆 `read_emails` + `unread_emails` 两表。**标已读 = 从 unread 删 + 插 read**。**用空间换查询性能**(NoSQL 常见手法)。


> 💡 **会话线程**:把回复和原邮件分组。靠邮件头的 **Message-Id / In-Reply-To / References** 三字段,用 **JWZ 算法**重建。**这是面试加分点**。

### 4.6 一致性权衡

```python
def send_smtp_with_retry(email, recipient_server):
    for attempt in range(MAX_RETRIES):
        try:
            smtp.deliver(email, recipient_server)
            return "sent"
        except (ConnectionError, ServerBusy) as e:
```

## 🪤 追问陷阱(面试官最爱问,本章集)

1. **"SMTP/POP/IMAP 区别?"** → SMTP 服务器间发送;POP 下载后删(单设备);**IMAP 留服务器多设备**(主流)。
2. **"邮件怎么找到收件服务器?"** → **DNS MX 记录**(带优先级,低的优先)。
3. **"附件怎么存?"** → **S3 对象存储**(大文件;Cassandra 不适合:blob 实际<1MB + 占行缓存)。元数据和附件分离。
4. **"为什么用队列?"** → 出站/入站队列**解耦 SMTP worker 与 web/SMTP 服务器**,各自扩缩 + 削峰缓冲。
5. **"同域邮件要走出站队列吗?"** → **不用**(同域快捷:直接入收件人存储)。
6. **"邮件实时推送怎么做?"** → 实时服务器 **WebSocket**(在线);离线存存储,上线 REST 拉(接 Vol.1 Ch12)。
7. **"Gmail 用什么存元数据?"** → **自定义分布式 DB**(Gmail 用 Bigtable)。关系库 BLOB 搜索差,对象存储难标记已读。
8. **"NoSQL 怎么查未读邮件?"** → **反规范化**:拆 read_emails + unread_emails 两表(NoSQL 只查分区/聚类键,is_read 不是键)。
9. **"邮件会话线程怎么实现?"** → 邮件头 Message-Id/In-Reply-To/References 三字段 + **JWZ 算法**。
10. **"为什么新邮件服务器发的邮件进垃圾箱?"** → **新 IP 没信誉**。要**专用 IP + 预热 2-6 周 + 分类发送**。
11. **"怎么防钓鱼?"** → **SPF + DKIM + DMARC**。SPF 授权 IP;DKIM 签名防篡改;DMARC 统一策略+报告。
12. **"hard bounce 和 soft bounce 区别?"** → hard=地址无效(永久拒);soft=临时(ISP 忙)。分独立队列。
13. **"邮件搜索用什么?"** → 小规模 **Elasticsearch**(倒排索引);Gmail 规模用**原生搜索(LSM 树,嵌入式)**免双系统同步。
14. **"邮件搜索 vs Google 搜索?"** → 邮件搜本人邮箱/按属性/近实时精确/写重于读;Google 搜全网/按相关性/索引有延迟。
15. **"2026 客户端协议?"** → **JMAP**(RFC 8621,HTTP/JSON,比 IMAP 快数倍)。
16. **"群发同附件怎么省存储?"** → **内容寻址去重**(hash 相同只存一份),省 PB 级。
17. **"邮件一致性怎么保证?"** → 每邮箱**单 primary**,failover 暂停访问(牺牲可用换一致)。

**核心 Takeaways**:

1. **邮件是存储极重型**(730PB元数据/年)——架构核心是存储优化:分布式元数据DB + 附件S3 + 去重 + 冷热分层。
2. **协议**:SMTP 服务器间发送;**IMAP 客户端读取主流**(多设备);DNS MX 定位收件服务器;附件 Base64+MIME。
3. **收发异步队列解耦**——出站/入站队列削峰 + 各自扩缩;同域邮件走快捷路径不走出站。
4. **实时推送**靠 WebSocket(在线);离线存存储上线 REST 拉(接 Vol.1 Ch12)。
5. **元数据建模**:Gmail 用自定义 DB(Bigtable);**反规范化**解决 NoSQL 读/未读查询(拆两表);**JWZ 会话线程**靠 Message-Id/In-Reply-To/References。
6. **每邮箱单 primary** 牺牲可用换一致(邮件正确性极重要)。
7. **送达率是现实最痛**——新 IP 没信誉要预热 2-6 周 + 分类发送 + 反馈环(hard/soft bounce/complaint)。
8. **防钓鱼三件套**:SPF(IP授权)+ DKIM(签名)+ DMARC(策略+报告);93% 数据泄露来自钓鱼。
9. **搜索**:小规模 Elasticsearch;Gmail 规模用原生 LSM(嵌入式,免双系统同步);邮件搜索写重于读。
10. **2026:JMAP 取代 IMAP**(HTTP/JSON 快数倍);Gmail 真实栈(Bigtable+Colossus+原生搜索+TensorFlow ML);附件去重省 PB;冷存储分层。
