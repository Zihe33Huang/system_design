## 1. 需求 + 估算

**两个 API**(背熟):
```
shorten(long_url)        → short_code   // 长链 → 短码
redirect(short_code)     → long_url     // 短码 → 长链(重定向)
```

**估算**(用 Ch2,假设 1 亿用户):
```
写(shorten):DAU 1亿 × 10% 创建 × 1 次 / 86400 ≈ 100 QPS
读(redirect):写 × 100(每个短链被点 100 次)≈ 1万 QPS
读写比 ≈ 100:1 → 缓存友好

存储:每条 short_code + long_url ≈ 500B
日增 100万 × 500B = 500 MB/天
10年 ≈ 1.8 TB × 3副本 ≈ 5 TB(小系统)
```

> 💡 **结论**:短链是**小系统**——单表 + KV + 缓存就够,不是分布式难题。难点在**短码生成方案**和**重定向方式**。

## 3. 301 vs 302 ⭐⭐(第一个核心抉择)

```mermaid
flowchart LR
    A["🟦 301 永久重定向<br/>────────<br/>• 浏览器缓存<br/>• 后续不再回源<br/>• 适合 SEO"] ~~~ B["🟪 302 临时重定向<br/>────────<br/>• 浏览器不缓存<br/>• 每次回源<br/>• 适合 Analytics"]

    style A fill:#E1F5FE,stroke:#0277BD,color:#1f1f1f
    style B fill:#F3E5F5,stroke:#7B1FA2,color:#1f1f1f
```

| | 301 永久 | 302 临时 |
|---|---|---|
| 浏览器缓存 | ✅ 缓存(后续直接跳,不回源) | ❌ 不缓存(每次回源) |
| 服务器压力 | 低(缓存后不再访问) | 高(每次都要查) |
| Analytics | ❌ 难统计(缓存后不回源) | ✅ **每次点击都能统计** |
| SEO | ✅ 权重传递 | ❌ 不传递 |
| 适用 | 永久跳转、SEO 优先 | **短链服务(要统计点击)** |

> 💡 **默认答案**:**短链服务用 302**——因为短链的核心价值之一是**统计点击**(Analytics),301 会被浏览器缓存,导致后续点击统计不到。原书没讲清这个场景。

> 🪤 **追问陷阱**:"为什么不用 301?" → "301 浏览器会缓存,后续点击不再回短链服务,**Analytics 统计不到**。短链要统计点击量,必须用 302(每次回源)。除非纯 SEO 场景才用 301。"

## 4. 短码生成:hash vs base62 ⭐⭐⭐(第二个核心抉择)

短码要求:**6-7 位、不可预测性可调、唯一**。两种主流方案:

```mermaid
flowchart TD
    Q["短码怎么生成?"] --> H["方案 A: hash<br/>MD5(long_url) 截断"]
    Q --> B["方案 B: base62<br/>自增 ID → base62 编码"]

    style Q fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style H fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style B fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
```

### 方案 A:hash(MD5 截断 + base62)

```mermaid
flowchart LR
    L["long_url"] --> H["MD5 哈希<br/>128 位"]
    H --> C["取前 6 位<br/>(base64 编码)"]
    C --> S["短码 (6 字符)"]

    style L fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style H fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style C fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style S fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
```

**做法**:`MD5(long_url)` → base64 → 取前 6 位。

| 优点 | 缺点 |
|------|------|
| **无状态**(同 URL 同短码) | **会冲突**(截断必然冲突) |
| 不需要 ID 生成器 | 冲突要查 DB 处理 |

> ⚠️ **冲突问题**:MD5 是 128 位,截断到 6 位(约 36 位)必然冲突(生日悖论:568 亿短码,几千条就可能冲突)。**必须查 DB 验证,冲突了换前缀重试**。

### 方案 B:base62(自增 ID + 编码)⭐ 推荐

```mermaid
flowchart LR
    ID["单调递增 ID<br/>(号段/自增, 见 Ch7)"] --> ENC["base62 编码"]
    ENC --> S["短码 (6 字符)"]
    S --> KV[("存 KV")]

    style ID fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style ENC fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style S fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style KV fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
```

**做法**:用 Ch7 的**号段模式(美团 Leaf)或 DB 自增**生成**小量级、单调递增**的 ID → base62 编码成短码。

> ⚠️ **关键陷阱(原书没强调)**:**不能直接用雪花!** 雪花 ID 量级 ~10^18,base62 编码后是 **11 位**,根本编不成 6 位短码。要 6 位,喂给 base62 的 ID 必须 < 568 亿(62^6)。详见下方"短码 ID 从哪来"。

> 📝 **base62**:`[0-9a-zA-Z]` 共 62 个字符。**6 位 base62 = 62^6 ≈ 568 亿** 种组合,够用。

**手算**:ID = 12345 → base62:
```
12345 = 3×62 + 51 → "35" (不断除 62 取余)
→ 短码 "3j"(补到 6 位)
```

| 优点 | 缺点 |
|------|------|
| **无冲突**(ID 唯一) | 同 URL 每次短码不同(除非加映射) |
| 短码长度固定 | 需要 ID 生成器(Ch7) |
| 可排序 | 可预测(可猜相邻 ID) |

### hash vs base62 决策

```mermaid
flowchart LR
    Q["同 URL 要返回同短码?"] -->|"是"| H["hash 方案<br/>(+ 冲突处理)"]
    Q -->|"否"| B["base62 方案 ⭐<br/>(号段/自增 ID + 编码)"]

    style Q fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style H fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style B fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
```

> 💡 **主流答案**:**base62 + 号段/自增 ID**(无冲突、可排序、6 位)。hash 方案的冲突处理麻烦,生产少用。**接上 Ch7 的号段模式(Leaf segment)**,不是雪花——这是综合题最常考错的点。

#### 深入:base62 编码手算 + 冲突概率 ⭐

**base62 编码**(面试可能让你写):
```python
BASE62 = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"
def to_base62(num):
    if num == 0: return "0"
    s = []
    while num:
        s.append(BASE62[num % 62])
        num //= 62
    return ''.join(reversed(s)).rjust(6, '0')   # 补到 6 位
```

**6 位短码容量**:62^6 = 56,800,235,584 ≈ **568 亿**。够任何短链服务用几十年。

**hash 方案冲突概率**(生日悖论):
- 6 位 base62 空间 568 亿
- 存 30 万条时,冲突概率 ~50%(生日悖论 k ≈ √N)
- 所以 hash 方案**必须查 DB 验证**

#### 深入:短码 ID 从哪来?(雪花 vs 号段 vs 自增)⭐⭐⭐(原书最大的隐藏坑)

**面试高频踩坑题**。很多人脱口而出"用雪花生成 ID 再 base62",但**这在数学上不成立**:

| ID 方案(见 Ch7) | ID 量级 | base62 编码长度 | 适合 6 位短链? |
|----------------|---------|----------------|----------------|
| **DB 自增** / **号段模式(美团 Leaf segment)** | 1 → 568 亿 | **6 位** | **⭐ 推荐** |
| Snowflake 雪花 | ~10^18(64 位) | **11 位** ❌ | 不适合(太长) |
| UUID / UUIDv7 | ~10^38 | ~22 位 ❌ | 完全不适合 |

> ⚠️ **关键数学**:6 位 base62 = 62^6 ≈ 568 亿。**喂给 base62 的 ID 必须 < 568 亿**才能编成 6 位。雪花 ID ≈ 10^18(高位是毫秒时间戳),`to_base62(snowflake)` 出来是 **11 位**,不是 6 位——这是最常见的面试翻车点。

> 💡 **正确接 Ch7**:短链的 ID 源 = **号段模式(Leaf segment)** 或 **DB 自增**,两者都是**小量级、单调递增**。号段模式给每个 server 发一段连续 ID(如 `1001~2000`),用完再申请,既高吞吐又保证 ID 小、连续、可排序(早期短码短、后期短码长,自然分代)。**雪花是给"超高吞吐、不在乎长"的场景**(消息 ID、订单 ID)用的,不是给短链用的。

> 🪤 **追问陷阱**:"为什么不用雪花?" → "雪花 ID 量级 10^18,base62 后 11 位,编不成 6 位短码。短链要小量级单调递增 ID,用**号段模式或 DB 自增**。"

#### 深入:短链安全(钓鱼 / 可枚举 / 恶意)⭐⭐(原书完全没讲,2026 高频追问)

短链天然**隐藏目标 URL**,是钓鱼/恶意传播的温床。这是 2020 版完全没覆盖、但面试官很爱追问的点:

| 安全风险 | 说明 | 2026 解法 |
|---------|------|----------|
| **钓鱼/恶意跳转** | 短码藏恶意 URL,用户点开才知道 | 后台**黑名单校验**(Google Safe Browsing API)、恶意 URL 拦截 |
| **可枚举** | base62 + 自增 → 相邻 ID 可遍历,爬虫能 dump 所有短链 | **不可预测盐**(ID + 随机盐再 hash)、限流、预生成随机短码池 |
| **过期/失效** | 短链被删/长链失效,仍可访问? | 设 TTL、404 页面、定期清理 |
| **滥用** | 大量创建指向同一长链 | 同长链返回同码(去重)+ 创建限流 |

```mermaid
flowchart LR
    USER["点击短链<br/>(未知目标)"] --> SRV["短链服务"]
    SRV --> SAFE{"安全检查<br/>黑名单/钓鱼库"}
    SAFE -->|"可疑"| BLOCK["拦截 + 警告页<br/>(预览真实 URL)"]
    SAFE -->|"安全"| R["302 → long_url"]
    SRV --> PREVIEW["提供预览<br/>(+ 号 / preview 页)"]

    style USER fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style SRV fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style SAFE fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style BLOCK fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
    style R fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style PREVIEW fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
```

> 💡 **预览惯例**:很多短链服务支持 `短码+` 或 `preview./短码` 显示真实目标(如 bit.ly 的 `+`)。面试讲到"安全"时主动提一句,加分项。

> 🪤 **追问陷阱**:"短链可枚举怎么办?" → "base62+自增能被遍历爬取。解法:① 短码混入**随机盐**(ID 不连续);② **预生成随机短码池**(从池里取,而非算);③ 加**限流**防 dump。"

## 6. Analytics(点击统计)

短链的价值不只是"短",还有**统计点击**(谁、何时、什么设备)。用 **302 重定向 + 埋点**:

```mermaid
flowchart LR
    USER["点击短链"] --> SRV["短链服务"]
    SRV --> LOG["埋点: user/time/device<br/>→ Kafka"]
    SRV --> R["302 → long_url"]
    LOG --> DW[("数据仓库<br/>点击分析")]

    style USER fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style SRV fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style LOG fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
    style R fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style DW fill:#90CAF9,stroke:#1976D2,color:#1f1f1f
```

> 💡 这就是为什么用 **302 而非 301**——每次点击都回源,才能埋点统计。

**redirect 时序**(含缓存未命中 + 埋点):

```mermaid
sequenceDiagram
    participant U as 浏览器
    participant S as 短链服务
    participant C as Redis 缓存
    participant D as 持久 KV
    participant K as Kafka

    U->>S: GET /abc123
    S->>C: GET url:abc123
    alt 缓存命中
        C-->>S: long_url
    else 缓存未命中
        C-->>S: nil
        S->>D: get(abc123)
        D-->>S: long_url
        S->>C: SET url:abc123 (回填)
    end
    S-)K: send clicks (异步埋点)
    S-->>U: 302 + Location: long_url
    U->>U: 跳转 long_url
```

## 💻 代码示例

### base62 + 号段完整流程

```python
import redis
r = redis.Redis()

def shorten(long_url):
    # 反查:同长链返回同码(去重 + 防滥用)
    code = r.get(f"long:{hash(long_url)}")
    if code: return code
    uid = leaf.next_id()                   # Ch7 号段模式(Leaf segment),非雪花!
    code = to_base62(uid)                  # uid < 568亿 → 6 位
    r.set(f"url:{code}", long_url)         # 正向:code → long_url
    r.set(f"long:{hash(long_url)}", code)  # 反向:long_url → code
    return code

def redirect(code):
    long_url = r.get(f"url:{code}")
    if not long_url:
        long_url = db.get(code)            # 缓存未命中查 DB
        if long_url: r.set(f"url:{code}", long_url)
    if long_url:
        kafka.send('clicks', {'code': code, 'time': now()})  # Analytics 埋点
        return 302, long_url               # 302 才能统计点击
    return 404
```

## 🪤 追问陷阱

1. **"301 还是 302?"** → 短链用 302(统计点击);纯 SEO 跳转用 301。
2. **"hash 还是 base62?"** → base62 + 号段/自增(无冲突);hash 要处理冲突。
3. **"为什么不用雪花生成短码?"** → 雪花 ID ~10^18,base62 后 11 位,编不成 6 位。用号段/自增(小量级 ID)。
4. **"6 位够吗?"** → 62^6 = 568 亿,够用。不够加到 7 位(3.5 万亿)。
5. **"怎么加速 redirect?"** → Redis 缓存热短码(命中率 >95%)。
6. **"同 URL 多次 shorten 返回同码吗?"** → base62 方案不同(每次新 ID);要相同则先查 `long_url → code` 反向索引。
7. **"短码可预测/钓鱼怎么办?"** → base62 可枚举。加限流 + 不可预测盐 + 黑名单 + 预览页。

**核心 Takeaways**:

1. **两个核心抉择**:301 vs 302(Analytics)、hash vs base62(冲突)。
2. **短链用 302**:每次回源才能统计点击——这是短链的核心价值之一。

**DynamoDB 表设计**(对标前面 SDE 笔记的 KV 模型):

| 属性 | 值 | 说明 |
|------|------|------|
| `short_code` (PK) | `"abc123"` | base62 短码,分区键 |
| `long_url` | `"https://long..."` | 长链 |
| `created_at` | 时间戳 | 创建时间 |
| `expires_at` | TTL 时间戳 | **配 DynamoDB TTL 自动过期删除**(短链天然有有效期) |
| `user_id` | 用户标识 | 配 GSI 做"查某用户的所有短链" |

> 💡 **DynamoDB TTL 是短链的免费午餐**:短链常要求"过期失效"(如营销活动链接)。直接给 item 设 `expires_at`,**DynamoDB 到点自动后台删除**,不用自己写清理任务。注意 TTL 删除有最多 48 小时延迟,精确到期要应用层校验。

**Lambda 伪代码(redirect)**:

```python
import boto3, json
ddb = boto3.resource('dynamodb').Table('urls')

def lambda_handler(event, context):
    code = event['pathParameters']['code']
    resp = ddb.get_item(Key={'short_code': code})
    item = resp.get('Item')
    if not item:
        return {'statusCode': 404, 'body': '{"error":"not found"}'}
    # 302 才能统计点击(见前面 SDE 笔记的 301 vs 302 抉择)
    return {
        'statusCode': 302,
        'headers': {'Location': item['long_url']}
    }
```

### 扩展:扛住流量(单 Region)

Day 0 跑通后,流量上来。**短链的典型模式是"读多写少"(100:1)**——一个名人发短链,几百万粉丝同时点。扩展的核心思路:**把重定向推到离用户最近的边缘缓存,根本不打到后端**。

    CF -->|"命中(99%)"| USER["直接 302 返回<br/><50ms"]
    CF -->|"未命中(1%)"| AGW["API Gateway"]
    AGW --> L["Lambda redirect"]
    L --> EC[("ElastiCache<br/>Redis 热码")]
    EC -->|"未命中"| DDB[("DynamoDB<br/>autoscaling")]

    style U fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style CF fill:#90CAF9,stroke:#1976D2,color:#1f1f1f
    style USER fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style AGW fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f

    style EC fill:#EF9A9A,stroke:#C62828,color:#1f1f1f

**四个扩展手段(按收益排序)**:

1. **CloudFront 缓存 301/302 重定向(最关键!)** ⭐⭐⭐⭐⭐
   - 重定向是 HTTP 响应,**天然可被 CDN 缓存**。配 `Cache-Control: max-age=300`,同一个短码 5 分钟内的所有点击都从边缘节点直接返回,**Lambda/DynamoDB 压力降 99%**。
   - **代价**:302 不能用了(每次回源统计点击),所以**对"不需要精确点击统计的短链"用 301 + CDN 缓存**;对"要统计的"仍走 302 但**接受少量未命中**。这是 SDE 笔记里"301 vs 302"抉择在 AWS 上的延伸——**缓存和统计是跷跷板**。

2. **DynamoDB on-demand 或 provisioned + autoscaling**
   - Day 0 用 on-demand;**流量稳定后切 provisioned + autoscaling 更省钱**(on-demand 单价是 provisioned 的 ~3 倍)。
   - 注意账号级 on-demand 配额(40k RCUs/WCUs),流量大要提前提配额。

3. **ElastiCache (Redis) 缓存热短链**
   - DynamoDB 单次 ~5-10ms,Redis ~1ms。**热短链(名人发的)放 Redis**,命中率 >95%。
   - **缓存失效**:配 DynamoDB Streams,Lambda 监听删除事件,**同步删 Redis key**(短链过期/删除时缓存要清,否则返回死链)。

4. **自定义短码防冲突:DynamoDB conditional write**
   - 用户要 `s.ly/mycustom`,得保证唯一。**DynamoDB `PutItem` 加 `ConditionExpression: attribute_not_exists(short_code)`**——并发写同一自定义码时,只有一个成功,其余 `ConditionalCheckFailedException` 重试。**这就是"乐观锁"在短链场景的标准做法**(对应 SDE 笔记"自定义短码优先于生成")。

```python
# 自定义短码:条件写防冲突
try:
    ddb.put_item(
        Item={'short_code': 'mycustom', 'long_url': long_url},
        ConditionExpression='attribute_not_exists(short_code)'
    )
except ClientError as e:
    if e.response['Error']['Code'] == 'ConditionalCheckFailedException':
        return {'statusCode': 409, 'body': '自定义码已被占用'}
```

> 💡 **扩展阶段的成本拐点**:CloudFront 缓存命中率每提高 10 个百分点,后端成本下降一个量级。**所以扩展阶段的头号优化不是加机器,是调缓存策略**(TTL、Cache-Control header、key 设计)。

**Day N 五件套**:

1. **多 Region active-active**:Route 53 延迟路由(用户去最近的 Region)+ **DynamoDB Global Tables** 双向复制映射表。**注意 ~1 秒复制延迟**:A 区刚生成的短码,B 区可能 1 秒内查不到 → 应用层重试或返回"稍后生效"。
   - **2024 re:Invent**:DynamoDB Global Tables 支持**强一致读**(多 Region),延迟更高但可对账,适合金融类短链(支付回跳)。

2. **WAF 防滥用**:CloudFront 前挂 **AWS WAF**——限频(单 IP 每分钟最多 N 次生成)、封恶意 UA、地理屏蔽。短链易被钓鱼/恶意使用,**WAF 是 Day N 的安全底线**。

3. **CloudFront 限流**:配 `rate-based rules`(1000 req/5min/IP 自动封 5 分钟),防短码枚举攻击(base62 可暴力枚举 6 位码)。

4. **短链过期 + 分析**:
   - 过期:**DynamoDB TTL** 自动删(配 `expires_at`)。
   - 分析:Lambda redirect 异步把点击事件发 **Kinesis Firehose → S3 → Athena**。**用 Athena 直接 SQL 查 S3**,不用建数据仓库(Serverless 全托管,按扫描量计费)。
   ```sql
   -- Athena: 查某短链最近 7 天点击量
   SELECT date_trunc('day', ts) AS day, count(*) AS clicks
   FROM clicks_bucket
   WHERE short_code = 'abc123' AND ts > now() - interval '7' day
   GROUP BY 1 ORDER BY 1;
   ```

5. **可观测**:CloudWatch 指标(`RedirectLatency`、`ShortenFailures`)+ 告警(错误率 > 阈值)+ **X-Ray 链路追踪**(看 Lambda→DynamoDB→ElastiCache 各段耗时)。对应 Part II `aws_12` 的监控三件套。

> 🪤 **Day N 陷阱**:
> - **Global Tables 复制延迟**:多 Region 写同一自定义短码可能都"看似成功"但最终冲突 → **全局唯一自定义码要加 Region 前缀**(`us-abc123`),或接受最终一致。
> - **CloudFront 缓存与更新**:长链改了(同一短码指向新 URL),但 CDN 缓存还在 → **缓存失效要主动发 `invalidation`**,或给改长链场景禁用缓存。
> - **WAF 误杀**:限频规则太严会误杀正常高并发用户(公司 NAT 出口共用 IP),**要给已知白名单 IP 放行**。

### 💰 成本与性能要点

| 维度 | 优化点 | 说明 |
|------|--------|------|
| **重定向延迟** | CloudFront 边缘缓存 | 全球 <50ms(命中缓存);未命中 ~50-100ms(Lambda+DDB) |
| **DynamoDB 成本** | on-demand(早期)→ provisioned+autoscaling(稳定) | 流量稳定后 provisioned 省 ~70% |
| **Lambda 冷启动** | provisioned concurrency / SnapStart(Java) | 短链逻辑极轻,冷启动通常 <200ms,问题不大 |
| **ElastiCache 成本** | 只缓存 Top-N 热短链 | 全量缓存太贵,LRU 驱逐冷数据 |
| **跨区流量费** | Global Tables 复制 + CloudFront 回源 | 跨区 $0.02/GB,Day N 多 Region 要算进预算 |
| **Athena 查询** | 用分区列 + 列式格式(Parquet) | 按扫描量计费,分区可降 90% 成本 |

> 💡 **成本心智(背)**:**短链的存储成本极低**(1KB/条,10 亿条才 1TB),**主要成本是读流量**。所以**缓存命中率是成本命门**——CloudFront + ElastiCache 把命中率做到 99%,后端 DynamoDB 几乎不打钱。**这正是为什么 AWS 短链是 Serverless 标杆场景**。

1. **CloudFront Functions(边缘轻量重定向)⭐⭐⭐⭐⭐**
   - **最颠覆短链架构的增量**:在 CloudFront 边缘节点跑**轻量 JS(执行 <1ms)**,**直接在边缘做短码→长链查表 + 返回 302,连 Lambda 都不用调**。
   - 配合一个轻量 KV(CloudFront KeyValueStore),把热短码映射放边缘 → **全球 <10ms 重定向,完全无后端**。
   - **话术**:"原书 Day N 还要 Lambda + DynamoDB 回源。2026 可以把热映射放 **CloudFront Functions + KeyValueStore**,**重定向在边缘节点完成,后端零调用**。这是短链场景的'极致 Serverless'。"

2. **DynamoDB Global Tables 强一致读(2024 re:Invent)⭐⭐⭐⭐**
   - 原书说 Global Tables 只能最终一致(~1 秒延迟)。**2024 起,Global Tables 支持多 Region 强一致读**——适合支付回跳短链这类"绝对不能跳错"的场景。代价是延迟更高、成本更高。

3. **S3 Express One Zone(超低延迟对象)⭐⭐⭐**
   - 若短链要批量存原始数据(如点击日志的中间态),**S3 Express One Zone 比标准 S3 快 10×**(个位数毫秒级首字节)。延迟敏感的批处理场景可选。

4. **Lambda 响应流(Response Streaming)⭐⭐⭐**
   - Lambda 可流式返回响应。短链场景可用于"**预览页**"(短链点击先弹预览页再跳转)的渐进式渲染,改善首屏体验。

> 🔄 **2026 话术(直接背)**:"AWS 书原版讲 Day N 还要 Lambda + DynamoDB 回源做重定向。但 **2024-2026 最大的变化是 CloudFront Functions + KeyValueStore**——可以把热短码映射直接放边缘节点,**重定向在 <1ms 内完成,后端零调用**,全球 <10ms。再配 DynamoDB Global Tables 强一致读(2024 新)做冷启动兜底,这就是 2026 短链的'极致 Serverless'形态。"
