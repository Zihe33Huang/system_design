## 3. 五种限流算法 ⭐⭐⭐⭐⭐(本章核心)

### 算法 1:令牌桶 (Token Bucket)——主流首选

```mermaid
flowchart LR
    R["Refiller<br/>每秒加 2 token"] -->|"持续投放"| B["Bucket<br/>容量 = 4"]
    REQ["请求来了"] --> Q{"桶里有 token?"}
    Q -->|"是"| PASS["放行<br/>消耗 1 token"]
    Q -->|"否"| DROP["拒绝 429"]

    style R fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style B fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style REQ fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style Q fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style PASS fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style DROP fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
```

**两个参数**:`bucket size`(容量)+ `refill rate`(每秒投放数)。

**关键特性**:**允许突发**——桶满时瞬时能放行 capacity 个请求。这是它被 Amazon、Stripe 选用的原因。

**Bucket 怎么分?**(追问高频):
- 每个 API endpoint 一个 bucket
- 每个 user/IP 一个 bucket
- 全局一个 bucket(限总 QPS)

| 优点 | 缺点 |
|------|------|
| 简单、内存省 | 两参数调优有难度 |
| **允许突发**——主流场景都需要 | — |

> 🏭 **真实产品**:Amazon API Gateway、Stripe 都用令牌桶。

### 算法 2:漏桶 (Leaky Bucket)——平滑输出

```mermaid
flowchart LR
    IN["请求流入<br/>(可能突发)"] --> Q["FIFO 队列<br/>容量 = N"]
    Q -->|"固定速率出"| OUT["处理<br/>(平滑)"]
    Q -->|"队列满"| DROP["拒绝"]

    style IN fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style Q fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style OUT fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style DROP fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
```

**特点**:请求以**固定速率**被处理(出桶),突发请求排队,队列满则拒绝。适合**需要稳定输出速率**的场景。

| 优点 | 缺点 |
|------|------|
| 内存省 | 突发填满队列后,**新请求被拒**(老请求占位) |
| 输出速率稳定 | 两参数调优 |

> 🏭 **真实产品**:Shopify 用漏桶。

### 算法 3:固定窗口计数 (Fixed Window Counter)——最简单但有临界突发

```mermaid
flowchart TD
    W0["窗口 0<br/>0:00-1:00<br/>counter 2/3"] --> W1["窗口 1<br/>1:00-2:00<br/>counter 3/3 ✅"]
    W1 --> W2["窗口 2<br/>2:00-3:00<br/>counter 1/3"]

    style W0 fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style W1 fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style W2 fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
```

**致命缺陷——临界突发**:限制 5 次/分钟。0:55 来 5 个,1:05 又来 5 个——1 分钟内(0:30-1:30)实际过了 **10 个**,是限额的 2 倍。

| 优点 | 缺点 |
|------|------|
| 内存省、好懂 | **临界点突发**——窗口边界可双倍放量 |

### 算法 4:滑动窗口日志 (Sliding Window Log)——最精确但耗内存

```mermaid
flowchart LR
    REQ["新请求"] --> RM["① 移除过期时间戳<br/>(> 窗口起点)"]
    RM --> ADD["② 加入当前时间戳"]
    ADD --> CNT{"③ 日志数 ≤ 限额?"}
    CNT -->|"是"| OK["放行"]
    CNT -->|"否"| REJ["拒绝(时间戳仍保留!)"]

    style REQ fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style RM fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style ADD fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style CNT fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style OK fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style REJ fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
```

**特点**:精确记录每次请求时间戳(用 Redis sorted set),任意滚动窗口内都不会超限。

| 优点 | 缺点 |
|------|------|
| **最精确**——任意窗口都不超 | **耗内存**(拒绝的请求时间戳也存) |

### 算法 5:滑动窗口计数 (Sliding Window Counter)——平衡之选 ⭐

```mermaid
flowchart LR
    REQ["新请求 @<br/>当前窗口 30%处"] --> CALC["估算 = 当前窗口计数<br/>+ 前窗口计数 × 重叠比例"]
    CALC --> Q{"估算 ≤ 限额?"}
    Q -->|"是"| OK["放行"]
    Q -->|"否"| REJ["拒绝"]

    style REQ fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style CALC fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
    style Q fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style OK fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style REJ fill:#EF9A9A,stroke:#C62828,color:#1f1f1f
```

**手算例子**:限 7 次/分钟。前窗口 5 次,当前窗口 3 次,新请求在当前窗口 30% 处:
```
估算 = 3 + 5 × (1 - 0.3) = 3 + 3.5 = 6.5 → 下取整 6 ≤ 7,放行
```

| 优点 | 缺点 |
|------|------|
| 平滑突发、内存省 | **近似**(假设前窗口均匀分布)——但 Cloudflare 实测 4 亿次里仅 0.003% 误判 |

> 🏭 **真实产品**:**Cloudflare** 用滑动窗口计数(亿级流量验证)。

> 📝 **名词注释**:**Rate limiting rules**(限流规则)——配置文件定义(Lyft 开源的 ratelimit 是工业模板),如"营销短信每用户每天 5 条""登录每分钟 5 次"。

## 5. 分布式限流的两个难点 ⭐⭐⭐(原书重点,但没讲透)

单机限流简单。**多机分布式**有两大坑:

### 难点 1:竞态条件 (Race Condition)

```mermaid
sequenceDiagram
    participant A as 请求A
    participant B as 请求B
    participant Redis
    Note over A,Redis: ❌ 非原子的"读-判-写"
    A->>Redis: GET counter (=3)
    B->>Redis: GET counter (=3)
    Note over A,B: 都读到3, 都判断"未超限"
    A->>Redis: INCR counter (=4)
    B->>Redis: INCR counter (=5)
    Note over Redis: 实际5, 但两个都放行了 → 超限!
```

**问题**:高并发下,"读 counter → 判断 → 写回"不是原子的,两个请求同时读到旧值,都放行,导致**实际超限**。

**解法**(原书只提了名字,这里讲透):

```mermaid
flowchart TD
    SOL["解法"] --> S1["① Lua 脚本<br/>Redis 单线程执行, 天然原子"]
    SOL --> S2["② Sorted Set<br/>滑动窗口日志的原子实现"]

    style SOL fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style S1 fill:#A5D6A7,stroke:#388E3C,color:#1f1f1f
    style S2 fill:#80DEEA,stroke:#0097A7,color:#1f1f1f
```

> 💡 **为什么 Lua 能解决**:Redis 是**单线程**执行命令的。把"读-判-写"写进一个 Lua 脚本,Redis 会**原子地执行完整个脚本**,中间不会插入其他命令。这是分布式限流的标准解法。

### 难点 2:多限流器节点的同步

```mermaid
flowchart LR
    C1["Client 1"] --> RL1["限流器1<br/>(本地计数)"]
    C2["Client 2"] --> RL2["限流器2<br/>(本地计数)"]
    Note["问题: 各自计数,<br/>全局超限"]
    RL1 -.->|"共享"| R[("集中式 Redis")]
    RL2 -.->|"共享"| R

    style C1 fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style C2 fill:#FFE082,stroke:#F9A825,color:#1f1f1f
    style RL1 fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style RL2 fill:#FFCC80,stroke:#F57C00,color:#1f1f1f
    style R fill:#CE93D8,stroke:#7B1FA2,color:#1f1f1f
```

**问题**:web 层无状态,同一用户的请求可能打到不同限流器,各自本地计数 = 全局失效。

**解法**:**集中式 Redis**(所有限流器共享一个 Redis)。原书提到 sticky session 不推荐(不 scalable),集中存储是正解。

> 🪤 **追问陷阱**:"集中式 Redis 会不会成瓶颈/单点?" → "① Redis Cluster 分片;② 本地缓存 + 定期同步(容忍少量超限);③ 多机房各部署 Redis + 最终一致。"——这是高级追问。

#### 深入:令牌桶手算 + Lua 实现 ⭐⭐

**令牌桶手算**(面试可能让你演算):

参数:容量 4,补充速率 4 个/分钟。初始桶满(4 个)。

```
t=0:   桶=4
t=10s: 来 3 个请求 → 消耗 3,桶=1,全放行
t=20s: 来 2 个请求 → 消耗 1(桶只有1),放行1,拒绝1,桶=0
t=60s: 补充 4 个 → 桶=4(满)
t=61s: 来 5 个请求 → 放行4,拒绝1,桶=0
```

> 💡 **手算用离散补充**(每分钟边界一次性补 4 个)便于演算;**生产令牌桶是连续补充**(每过 dt 补 `rate × dt` 个,如下方 Lua)。两者模型不同,面试演算用离散即可,但要说明"生产是连续补充"。

**Lua 脚本实现令牌桶**(可直接背,面试白板能写):

```lua
-- KEYS[1] = bucket key, ARGV = [capacity, refill_rate, now, cost]
local key = KEYS[1]
local capacity = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])       -- token / second
local now = tonumber(ARGV[3])
local cost = tonumber(ARGV[4])

local bucket = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(bucket[1]) or capacity
local ts = tonumber(bucket[2]) or now

-- 按经过时间补充 token
local delta = math.max(0, now - ts)
tokens = math.min(capacity, tokens + delta * rate)

local allowed = 0
if tokens >= cost then
    tokens = tokens - cost
    allowed = 1
end

redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
redis.call('EXPIRE', key, 120)
return allowed
```

> 💡 **关键点**:整个"读 tokens → 算补充 → 判断 → 写回"在 Lua 里**原子执行**,解决竞态。

## 7. 性能优化 + 监控

**性能**:
- **多机房部署**:用户就近访问边缘节点(Cloudflare 全球 330+ 节点)。
- **最终一致同步**:多机房 Redis 异步同步,容忍少量误差。

**监控 2 个指标**:
1. **算法是否有效**:突发时(秒杀)令牌桶是否挡住了。
2. **规则是否合理**:太严→大量正常请求被拒(放松);太松→限流形同虚设。

## 💻 代码示例

### Python 滑动窗口计数(Redis sorted set 实现)

```python
import redis, time
r = redis.Redis()

def rate_limit_sliding(user_id, limit=100, window=60):
    key = f"rl:{user_id}"
    now = int(time.time() * 1000)
    window_start = now - window * 1000
    pipe = r.pipeline()
    pipe.zremrangebyscore(key, 0, window_start)   # 移除过期
    pipe.zadd(key, {str(now): now})               # 加当前
    pipe.zcard(key)                                # 数当前窗口内
    pipe.expire(key, window)
    _, _, count, _ = pipe.execute()
    return count <= limit
```

### 多级限流(实际场景)

```python
def check(user_id, ip, api):
    return all([
        rate_limit(f"user:{user_id}", limit=1000),   # 用户级
        rate_limit(f"ip:{ip}", limit=500),           # IP 级(防刷)
        rate_limit(f"api:{api}", limit=10000),       # API 全局
    ])
```

> 💡 **多级限流是 2026 实战标配**:用户级防滥用 + IP 级防爬虫 + API 全局防过载,三层叠加。

## 🪤 追问陷阱

1. **"令牌桶和漏桶区别?"** → 令牌桶**允许突发**(桶满瞬时放行 capacity 个);漏桶**平滑输出**(固定速率出)。
2. **"高并发下计数不准怎么办?"** → Redis + **Lua 原子脚本**(单线程执行)。
3. **"多机房限流怎么做?"** → 集中 Redis Cluster + 异步同步,容忍少量超限;或全局令牌桶服务。
4. **"Redis 挂了限流怎么办?"** → fail-open(放行,保业务)还是 fail-close(拒绝,保后端)?**默认 fail-open + 告警**,业务连续性优先。
5. **"令牌桶参数怎么调?"** → capacity 设为峰值 QPS × 容忍突发秒数;refill rate 设为平均 QPS。
6. **"限流和熔断区别?"** → 限流是**入口防御**(超量拒绝);熔断是**下游保护**(下游挂了快速失败,不拖垮自己)。
